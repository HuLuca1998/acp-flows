# 操作踩坑档案

> **这是 AI 的操作记忆。** 每条都是本项目里真实花了时间才解决的问题——
> 记在这里是为了让下一个 AI 不用再花一次。

> **读法**：**不要整篇读。** 你是带着一个症状来的，按下面的症状索引 grep 到那一条即可。
>
> ```bash
> grep -n "你看到的报错原文" docs/notes/pitfalls.md
> ```

## Shell 与脚本

### P-01

**`set -e` 下 `[[ 条件 ]] && 命令`，条件为假时整个脚本静默退出**

- **症状** 脚本跑到一半就结束，退出码非 0，但**一条错误信息都没有**。后面的检查看起来"通过了"，其实根本没跑。
- **根因** 条件为假时 AND-list 返回 1。它若是函数或循环体的**最后一条语句**，`set -e` 就地终止。
- **解决** 循环体、函数体末尾一律用 `if ... fi`，不要用 `&&` 简写。
- **教训** 这条**已经踩过 4 次**（`check-naming` / `check-i18n` / `check-doc-budget` 各一次）。
  记在文档里没能挡住它——因为写脚本的人不会先去读脚本目录的文档。
  **真正的防线是：每个检查脚本写完必须先制造一次违规、确认它真的会红。**
- **状态** 活跃。失效条件：所有检查脚本改用 `set -o errexit` 之外的机制。

### P-02

**`pipefail` + `grep` 无匹配 / `find` 撞权限错误 → 整条管道失败**

- **症状** `grep` 找不到东西是正常结果，脚本却当成错误退出。
- **解决** `{ grep ... || true; }`，`find ... 2>/dev/null || true`。
- **教训** 区分「命令失败」和「命令成功但结果为空」。`grep` 的退出码 1 是后者。
- **状态** 活跃。

### P-03

**`case` 分支的 `)` 出现在 `$( ... )` 内部 → 括号失配**

- **症状** `syntax error near unexpected token ';;'`，但那一行看起来完全正常。
- **根因** 命令替换 `$( )` 里嵌 `case`，解析器把 `分支)` 的右括号当成替换结束。
- **解决** 在 `$( )` 里改用 `if [[ ]]`，`case` 只在顶层用。
- **状态** 活跃。

### P-04

**`find -not -path './node_modules/*'` 只排除顶层，不排除嵌套**

- **症状** 检查脚本把 `frontend/node_modules/` 里几千个第三方 README 当成项目文档扫了。
- **解决** 用 `-prune`，或同时写 `-not -path './node_modules/*' -not -path '*/node_modules/*'`。
- **教训** `-path` 匹配的是**完整路径字符串**，`./node_modules/*` 匹配不上 `./frontend/node_modules/x`。
- **状态** 活跃。

### P-05

**macOS 自带的 bash 是 3.2，没有 `mapfile` / `readarray` / 关联数组**

- **症状** `mapfile: command not found`，但在 Linux CI 上跑得好好的。
- **解决** `arr=(); while IFS= read -r x; do arr+=("$x"); done < <(...)`。
- **教训** 本仓库脚本必须同时能在 **macOS bash 3.2** 和 **CI 的 bash 5** 上跑。
  用 bash 4+ 特性之前先想清楚。
- **状态** 活跃。

### P-06

**`nohup` 起的后台进程继承父进程 stdout 管道 → `make` 挂住不返回**

- **症状** `make dev` 服务确实起来了，但命令不返回，一直卡着。
- **根因** `make` 用管道捕获输出，后台进程持有那个管道的写端不放，管道读端就永远等不到 EOF。
- **解决** 三处都要断开：`( ... ) </dev/null` 包住，内部 `nohup cmd </dev/null >log 2>&1 &`。
- **状态** 已修（`scripts/dev/services.sh`）。失效条件：改用 launchd / systemd 之类的进程管理器。

## Git

### P-07

**`git reset --hard` 把未提交的工作一起抹掉**

- **症状** 刚写好的一批改动没了，且不在 `git stash` 里。
- **教训** `--hard` 抹的是工作区，不区分"我想丢的"和"我还没提交的"。
- **解决** 想回退提交但保留改动用 `--soft`；**动 git 历史之前先 `git add -A && git commit`**，
  哪怕是个临时提交——后面可以 squash，丢了的东西找不回来。
- **状态** 活跃。这条**已经真实损失过一次**（多 scope 提交规则的改动全部重写）。

## Go 与工具链

### P-08

**`io.Pipe` 是同步的，测试**挂住**而不是失败**

- **症状** `go test` 不结束，也不报错，最后被超时杀掉。
- **根因** `io.Pipe` 的 `Write` 阻塞到有人 `Read`。测试夹具里只写不读就死锁。
- **解决** 起一个后台 goroutine 持续 drain，读取侧加超时。
- **教训** **测试挂住比测试失败更危险**——CI 上表现为"慢"，容易被当成环境问题重跑。
  任何涉及 pipe / channel / 子进程 stdio 的测试，都要给读取加超时。
- **状态** 活跃。

### P-09

**golangci-lint 的 `issues.uniq-by-line` 默认是 `true`，会吞掉同一行的第二条报错**

- **症状** `.golangci.yml` 里配了 depguard 分层规则，但故意写一个越界 import 也不报。
  **规则看起来配好了，其实是哑的。**
- **根因** 同一行若 revive 先报了，depguard 的消息被去重丢弃。
- **解决** 显式 `issues.uniq-by-line: false`。
- **教训 ★** 这是**「配置了 ≠ 生效了」的典型**。任何新加的 lint 规则、检查脚本、
  CI 步骤，都必须**故意制造一次违规，确认它真的会红**——这一步不能省。
- **状态** 已修。失效条件：golangci-lint 改默认值。

## 前端工具链

### P-10

**vite 6 与 vitest 2 的类型不兼容**

- **症状** `tsc` 报错指向 `node_modules/vite` 里的类型定义，业务代码一行没改。
- **解决** 锁 `vite ^5.4.11`。
- **状态** 活跃。失效条件：升级到 vitest 3（届时应改回 vite 6 并删掉这条）。

### P-11

**eslint 的 `disableTypeChecked` 放在 `recommendedTypeChecked` 之前会被覆盖**

- **症状** 明明关掉了对某些文件的类型检查，还是报错。
- **根因** flat config 是后者覆盖前者。
- **解决** `disableTypeChecked` 必须排在后面。
- **状态** 已修。

### P-12

**pnpm 的字段是 `allowBuilds`，不是 `onlyBuiltDependencies`**

- **症状** `ERR_PNPM_IGNORED_BUILDS`，**所有** make 目标都跑不动（因为都依赖 install）。
- **教训** 包管理器配置写错的杀伤面是全局的。改完立刻跑一次 `make check` 验证。
- **状态** 已修。

## GitHub Actions

### P-13

**Actions 缓存是 ref-scoped —— tag 触发的工作流读不到 main 上的缓存**

- **症状** Release 工作流比 CI 慢 6 分钟，缓存全 miss，但 key 明明一样。
- **根因** 缓存按 ref 隔离；`refs/tags/v1.2.3` 与 `refs/heads/main` 是两个作用域。
- **解决** 发布改成 `workflow_dispatch` on main，不用 tag 触发。
- **出处** 前作 `~/work/ai-workflows` 实测，见 [`adr/0007`](../adr/0007-release-revision-from-prior-art.md)。
- **状态** 活跃。

### P-14

**Apple 证书：Actions 无法「条件性地 unset 环境变量」→ 必须写两个互斥的构建步骤**

- **症状** 没配证书的 fork 上构建失败：`failed to import keychain certificate`。
- **根因** `env: APPLE_CERTIFICATE: ${{ secrets.X }}` 在 secret 为空时传的是**空字符串**，
  不是「没有这个变量」。tauri-action 见到空串就去导入，然后炸。
- **解决** 写两个 `if:` 互斥的 step —— 一个带证书 env，一个完全不带。
- **状态** 活跃。

### P-15

**Apple Silicon 上 ad-hoc 签名必须显式写 `APPLE_SIGNING_IDENTITY: '-'`**

- **症状** 用户双击提示「**已损坏，无法打开**」——注意不是「未认证的开发者」。
- **根因** arm64 要求二进制**必须有签名**。完全没签名的产物被系统判为损坏，
  而不是判为未公证。两种提示对应两个完全不同的问题，容易查错方向。
- **解决** 显式 ad-hoc 签名 `APPLE_SIGNING_IDENTITY: '-'`。
- **状态** 活跃。

## 本项目的环境

### P-16

**`DUET_DATA_DIR` 是「家目录替身」，不是数据目录本身**

- **症状** 按 `$DUET_DATA_DIR/duet.db` 去连开发库，找不到文件或连出个空库。
- **根因** `platform.NewPathsAt(root)` 之后仍会拼上 `.acpflows/`，
  所以真实路径是 `~/.duet-dev/.acpflows/duet.db`，比想象的多一层。
- **状态** 活跃。

### P-17

**SQLite 的 `foreign_keys` 是「每连接」的，在 `sqlite3` CLI 里永远看到 0**

- **症状** CLI 里 `PRAGMA foreign_keys;` 返回 0，据此判断"外键没生效"，然后查错方向。
- **根因** 这个 pragma 属于连接，不属于库。CLI 自己的连接没带 DSN 参数，当然是 0。
  对比 `journal_mode` 是**库属性**，谁连都是 `wal`。
- **解决** 要验证应用侧，跑 `TestOpen_R1_ForeignKeysPragmaIsOn`，不要看 CLI。
- **状态** 活跃。

### P-18

**WAL 模式下 `cp duet.db` 拷不到数据 —— 备份必须用 `VACUUM INTO`**

- **症状** 备份文件大小正常，但打开后 `no such table: xxx`，或者行数比原库少。
- **根因** WAL 模式下已提交的数据可能还在 `-wal` 文件里没 checkpoint 到主库。
  只拷 `duet.db` 等于拷了个空壳。
- **解决** `VACUUM INTO '<目标路径>'` —— 一致性快照，不需要停写。
  注意它**要求目标文件不存在**，否则报 `output file already exists`，
  所以文件名带时间戳且不要预创建。
- **教训** 这条是探针实测发现的，而当时 `database.md` §5 写的正是「备份 `duet.db`
  到 `duet.db.bak`」——**文档里一个看起来无害的措辞，落成代码就是用户数据丢失**。
  裁定见 [`adr/0008`](../adr/0008-schema-migration-and-init.md) D4。
- **状态** 活跃。失效条件：改用非 WAL 模式（不会发生）。

## 维护规则

### 什么时候加一条

**两个条件同时满足**才记：

1. **花了 >15 分钟或试了 >2 次**才解决 —— 顺手解决的不记，记了会稀释信号
2. **会再次发生** —— 一次性的环境抽风不记

### 加之前先问：能不能变成检查

**这是第一动作，不是可选项。**

| 能变成什么 | 就写成什么 | 档案里留什么 |
|---|---|---|
| 检查脚本能拦 | 补进 `scripts/check-*.sh` | 压成一行，注明「已变成检查」 |
| 测试能拦 | 写一个回归测试 | 压成一行，写明测试名 |
| lint 能拦 | 加规则，**并故意违规验证它会红** | 压成一行 |
| 都拦不住（外部服务行为、平台差异） | —— | **完整记进本文** |

> 文档挡不住重复踩坑——P-01 记录在案还是被踩了 4 次。
> **能变成检查的坑不要写进文档，写进检查里。**

### 一条的格式

```markdown
### P-NN

**一句话说清是什么坑**

- **症状** AI 会实际观察到什么（★ 用报错原文，那是 grep 的钥匙）
- **根因** 为什么会这样
- **解决** 具体怎么做
- **教训** 可推广的那一句（没有就不写，别硬凑）
- **状态** 活跃 / 已修 / 已变成检查。**并写明失效条件**
```

**「症状」必须是 AI 能观察到的现象，不是根因的复述。**
AI 是带着报错原文来查的，索引表里没有那句原文，这条就等于不存在。

### 过期就删，不要留着

**每条都必须写失效条件。** 撞上失效条件时**当场删除整条**，不要改成
「~~已废弃~~」留在原地——留下的过期条目会被下一个 AI 当成有效信息。

必须删的情况：

- 依赖升级后不再成立（如 P-10 升到 vitest 3 之后）
- 相关代码/脚本已被删除或重写
- 已经变成检查，且那个检查在 CI 里跑 → 压成一行，不留长篇
- 复现不出来了 —— **先试着复现一次**，确实复现不出就删

删的时候顺手把**症状索引表**里那一行也删掉。索引指向不存在的锚点，
比没有索引更糟。

### 与目录 `AGENTS.md` 的分工

| 坑的性质 | 记哪 |
|---|---|
| 只在某个目录里会遇到（这个包的特殊约定） | 该目录 `AGENTS.md` 的「本域特有的坑」 |
| 跨域的操作类问题（工具链、平台、外部服务、命令行为） | **本文** |

**同一个坑只记一处。** 两处都写必然漂移。
