## 0. 你干活时产出了一份东西，它该去哪

**先判断它是哪一类，再决定去处。绝大多数情况的正确答案是「不新建文件」。**

| 你产出的东西 | 去哪 | 进 git |
|---|---|---|
| 一次性的调查 / 分析 / 对比 / 思考过程 | **不落盘**，写进 PR 描述或提交信息 | ✗ |
| 临时脚本、抓的日志、中间产物 | 系统 scratchpad 目录 | ✗ |
| 真机实测发现（"实际行为是 X 不是 Y"） | `docs/notes/` 对应文档**加一节** | ✓ |
| **踩的坑：跨域的、操作类的**（工具链 / 平台 / 外部服务） | [`docs/notes/pitfalls.md`](../notes/pitfalls.md) 加一条 | ✓ |
| 踩的坑：只在某个目录里会遇到 | 该目录 `AGENTS.md` 的「本域特有的坑」 | ✓ |
| 一条以后都得遵守的规则 | `docs/rules/` 对应文档**加一节** | ✓ |
| 系统某部分的规格说明 | `docs/spec/` 对应文档**加一节** | ✓ |
| 选了 A 不选 B，以后不重新讨论 | `docs/adr/NNNN-<slug>.md` **新建** | ✓ |
| 需要人拍板的问题 | `docs/plan/open-questions.md` 加一条 | ✓ |
| 新的开发计划 / 单元拆解 | `docs/plan/milestones/` | ✓ |

### 三条硬规矩

1. **默认是「加一节」，不是「新建文件」。**
   新建之前必须先答：这件事为什么不能作为某份已有文档的一节？答不上来就不要新建。
   > 松散的文档目录不是一次造成的，是每次「我这个比较特殊，单独开一份」累积出来的。

2. **`docs/` 根目录不接受新文件。** 新文档必须落进
   `spec/` `rules/` `notes/` `adr/` `plan/` 之一。`make check-docs` 会拦。

3. **新建了就要在 [`docs/README.md`](../README.md) 登记一行。** 没登记的文档等于不存在——
   没人（包括 AI）会 `ls` 一个目录去发现它。`make check-docs` 会拦。

### 什么根本不该进 `docs/`

- ✗ 你的思考过程、方案对比、"我考虑过 A B C 最后选了 B" —— 结论进 ADR，过程不留
- ✗ 任务完成报告、总结、进度快照 —— 那是提交信息和 PR 描述的事
- ✗ 代码怎么写的说明 —— 写成代码注释，或者说明这段代码本身需要重写
- ✗ 复制自其他文档的内容 —— 一件事只在一处写，别处用链接

> 判据：**这份文档会在什么时候、被谁、为了解决什么问题打开？**
> 答不上来就不要写它。

## 1. 关键目录的 `AGENTS.md` + `CLAUDE.md`

目录会越来越多。**每个"关键目录"都必须有成对的 `AGENTS.md` + `CLAUDE.md`；
缺失时，谁在这个目录里干活谁补上——这是任务的一部分，不是可选的收尾工作。**

### 什么算"关键目录"（可机器判定）

满足**任一**条件即为关键目录：

1. 顶层目录（`backend/` `frontend/` `shell/` `api/` `e2e/` `design/` `docs/` `scripts/`）
2. `backend/internal/` 下的任一一级子包
3. `frontend/src/` 下的任一一级子目录，以及 `frontend/src/features/` 下的任一一级子目录
4. 该目录**直接包含 ≥ 3 个源文件**（`.go` `.ts` `.tsx` `.rs`），无论层级多深

### 什么时候补

在**第一次**往一个关键目录里写文件时就补，和业务改动放同一个提交。
不要攒着以后统一补——攒着的结果永远是不补。

### 怎么补

```bash
make docs-scaffold DIR=backend/internal/store     # 从模板生成两份骨架
```

模板在 [`docs/templates/`](../templates/)。生成后**必须填实**下列内容，
留着占位符不算完成：

- **这个目录负责什么 / 不负责什么**（边界比职责更重要）
- **依赖方向**：允许 import 谁，禁止 import 谁
- **本域的检查命令**（怎么测、怎么 lint）
- **本域特有的坑**：踩过的、容易犯的错
- **改这里之前必读的文档**

`CLAUDE.md` 保持三行薄壳，指向同目录 `AGENTS.md`，**不要复制内容**——
两份内容一旦重复就必然漂移。

### 强制手段

```bash
make check-docs      # 列出所有缺失 AGENTS.md / CLAUDE.md 的关键目录
```

CI 在每个 PR 上跑这条。缺失即**红**，PR 合不进去。

### 内容过期也是缺陷 —— **过期就删，不是标注**

发现某段文档与实际对不上（描述了不存在的文件、写着已废弃的规则、
引用了删掉的命令），**当场处理**，不要绕开。文档滞后按缺陷处理，与代码 bug 同等对待。

**处理方式按情况分三种，注意第三种：**

| 情况 | 动作 |
|---|---|
| 描述错了，但这件事还存在 | **改对** |
| 这件事已经不存在了 | **整段删掉** |
| 这是一个已关闭的决策（ADR） | 旧 ADR 开头加 `> 已被 adr/00XX 取代`，**正文不动** |

> ★ **除 ADR 外，不要用「~~已废弃~~」「（历史遗留，勿用）」这类标注留在原地。**
> 留下的过期内容会被下一个 AI 当成有效信息读进去——它没有你的上下文，
> 分不清哪些是活的。**删掉它**。git 历史里找得回来，那才是留存的地方。

**主动扫描过期内容的手段**（这些是机器能查的，别靠眼睛）：

```bash
make check-doc-links      # 链接指向的文件还在吗
make check-doc-commands   # 文档里提到的 make 目标 / 脚本还在吗
make check-doc-budget     # 文档体量还在预算内吗
make check-docs           # 落位与索引登记
```

**每轮收尾跑一次。** 这四条挡不住的过期（比如描述了一个已被重写的算法），
靠你干活时撞见——撞见就删。

## 文档演进：发现问题就地改

**这套文档是活的，不是一次性写完就冻结的。**
第一版必然有想不到的地方——你在干活时撞上的每一个坑，都是文档的缺口。

### 触发条件 —— 撞上任一条就要动文档

| 你遇到了 | 动作 |
|---|---|
| 文档描述与实际代码对不上 | **当场修文档**，和业务改动同一个提交 |
| 文档没说清楚，你猜了一个做法 | 把你的判断写进去，**并标注这是新增的裁定** |
| 踩了坑（看起来对但其实错） | 写进该目录 `AGENTS.md` 的「本域特有的坑」 |
| 被审查打回 | 打回理由如果是通用的 → 补进规范或禁止清单 |
| 两份文档说法不一致 | 立刻合并到其中一处，另一处改成链接 |
| 规则没有强制手段，你发现有人（包括你）违反了 | **补检查脚本**，见 `docs/adr/0003` |
| 设计稿里找不到对应条目 | 登记进 `docs/frontend-guide.md` 的设计缺口表 |

### 什么时候当场改，什么时候开 issue

| | |
|---|---|
| **当场改** | 事实性错误、过期描述、缺一条坑、缺一条禁止项、措辞含糊 |
| **开 issue** | 需要改变架构决策、需要人拍板的取舍、要动 ADR |

**当场改的门槛要低。** 犹豫「这算不算越界」时——改文档不算越界，
铁律 4 管的是代码写入边界，不管文档修正。

### 怎么改

- 加规则的同时问：**这条怎么被 CI 拦？** 拦不了就改成能拦的形式，
  或明确标注「靠自觉，可能失效」
- **一件事只在一处写。** 需要交叉引用用链接，不要复制
- 数值要具体（`400 行`，不是「不要太长」）；不写「应该」「尽量」「建议」
- 架构决策变了 → **写新 ADR**，旧 ADR 开头加 `> 已被 adr/00XX 取代`，不改旧正文

### 每轮收尾必做

- [ ] 这次踩的坑写进对应 `AGENTS.md` 了吗？
- [ ] 这次的改动让哪份文档过期了？改了吗？
- [ ] 有没有发现「规则存在但没人执行」的？补检查了吗？

**文档滞后按缺陷处理，与代码 bug 同等对待。** 攒着以后统一修的结果永远是不修。
