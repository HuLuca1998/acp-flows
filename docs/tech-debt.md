# 技术债：发现、判定、铲平

> **原则：不在屎山上堆屎。**
>
> 但这条和铁律 4「不扩大边界」天然打架。判定标准必须写死，
> 否则 AI 要么不敢动（债务复利增长），要么借"重构"之名乱改（边界形同虚设）。
> 本文就是那条判定标准。

---

## 1. 最危险的一句话：「跟现有代码保持一致」

AI 制造屎山的**头号路径**：

> 「这个包里现有的代码都是这么写的，所以我也这么写。」

**与错误的模式保持一致，是在扩散错误。** 一致性是好东西，但它服从于正确性。

正确的反应是三选一，**不许有第四种**：

| 你的处境 | 动作 |
|---|---|
| 这个错误模式挡着我，不铲就写不下去 | **先铲平**（§3），独立提交，再往上加 |
| 不挡路，但我确实看见了 | **开 issue** 登记进 §5 债务表，按原样继续，**并在 PR 里说明** |
| 我不确定这算不算错 | **停下来问**，不要自己拍板扩大重构 |

**"照着抄一遍然后什么都不说"不在选项里。**

## 2. 屎山的具体信号

不要用"代码看着不顺眼"这种感觉判断。以下是**可指认的**信号：

### 结构信号

- 一个包里平铺 > 10 个文件；按技术种类切文件（`models.go` `utils.go` `handlers.go`）
- 单文件 > 400 行 / 单函数 > 60 行
- 两处以上近乎相同的代码（复制粘贴复用）
- `switch` 分发同类实现（加第 3 个要改老代码）
- 上帝接口 / 上帝文件
- 接口和它唯一的实现在同一个包

### 分层信号

- `domain` 里出现 `context.Context`、`time.Now()`、SQL、HTTP
- `app` 里拼 SQL 或直接起进程
- `api` 里写业务判断
- 前端非 `platform/` 文件 import `@tauri-apps/*`
- 生产代码 import `tests/testutil`

### 测试信号

- 测试存在但删掉实现关键行仍然绿（**假测试**）
- 一个行为有三个名字不同的测试（`TestCancelWorks` / `TestCancelSuccess` / `TestSessionCancelBasic`）
- `t.Skip()` / 被注释掉的断言
- 测试碰真实 `~/.acpflows`、真实仓库、真实网络

### 文档信号

- `AGENTS.md` 描述的文件/规则已不存在
- 两份文档对同一件事说法不一致
- 规则存在但没有任何检查手段，且已经有人违反

**每一条都对应一份规范里的硬规则**，不是主观judgment：
[`design-principles.md`](design-principles.md) · [`coding-standards.md`](coding-standards.md) ·
[`testing-strategy.md`](testing-strategy.md) · [`architecture.md`](architecture.md)。

## 3. 铲平流程

### 判定：挡路还是路过

**挡路**（必须先铲）：

- 不改它，我这次的改动就得复制粘贴
- 不改它，我这次的改动就得违反分层
- 不改它，我写不出能真正验证行为的测试
- 它是我这次要改的那个文件/函数本身

**路过**（登记，别顺手改）：

- 我改的是 A，看见 B 有问题，A 和 B 没有调用关系
- 需要动的文件数量超过本次任务允许范围的两倍
- 需要改公开接口、数据库 schema、OpenAPI 契约

### 挡路的怎么铲：五步

```
① 先给现状补测试         —— 锁住当前的外部行为，这一步是安全网
② 跑，确认新测试是绿的    —— 它描述的是"现在的行为"，本来就该绿
③ 重构，测试保持绿        —— 行为不变，只改结构
④ 独立提交               —— refactor(scope): …，与业务改动分开
⑤ 再做原本要做的事        —— 回到 tdd-unit 的正常流程
```

**第 ①② 步不能跳。** 没有安全网的重构等于赌博——
你不知道自己改坏了什么，因为原来就没测试。

**第 ④ 步不能省。** 重构和业务改动混在一个提交里，
审查方无法判断哪些行为变化是有意的。这是审查打回的常见理由。

### 铲平的边界

铲平**也有边界**，不是免死金牌：

- 只铲**挡路的那一块**，不顺手把整个包重写
- 不改公开接口、不改数据库 schema、不改 OpenAPI —— 那些属于 `contract_revision`，停下来找人
- 铲平的范围要在 PR 描述里写清楚，和业务改动的范围分开列

### 铲不动的时候

范围超出可控 → **停下来上报**，判定为：

| 判定 | 含义 |
|---|---|
| `contract_revision` | 需要改契约或接口才能铲干净 |
| `global_replan` | 架构假设本身错了，需要重新规划 |

**不要硬着头皮铲一半。** 铲一半的结果是新旧两套模式并存，比原来更烂。

## 4. 每轮必做的债务体检

`tdd-unit` skill 第 ⑦ 步的一部分：

- [ ] 我这次是不是"照着现有的错误模式又写了一遍"？
- [ ] 我这次有没有复制粘贴？（有 → 抽出来）
- [ ] 我碰过的文件里，有没有 §2 里能指认的信号？
- [ ] 挡路的铲了吗？路过的登记了吗？
- [ ] 我这次的改动会不会成为下一个人的屎山？

最后一条最重要。**你写的每一行都会被下一轮 AI 当作"现有模式"照抄。**

### 登记规则

- **状态只有 `open` / `paying`（正在还）/ `paid`（已还，写上 PR 号）**
- `open` 超过一个里程碑没还 → 在下个里程碑规划时**必须**重新评估：还是不还，明确决定
- 还完了不要删行，改成 `paid` 并注明 PR —— 历史记录有价值
- **这张表不许无限增长。** 超过 10 条 `open` 说明在系统性地欠债，
  停下来找人，安排一次专门的偿还

## 6. 什么不算技术债

别把这些登记进来，会稀释真正的债务：

- ✗ 「我更喜欢另一种写法」—— 风格偏好不是债
- ✗ 「这里可以更优雅」—— 没有具体代价的不是债
- ✗ 「以后可能需要抽象」—— 猜测中的需求不是债
- ✗ 「这个函数名我不喜欢」—— 除非它违反了命名规范

**债务的定义：它现在正在或即将让改动变慢、变危险、或变得容易出错。**
说不出具体代价的，不是债。

---

## 7. 禁止清单

- ✗ 「跟现有代码保持一致」当作照抄错误模式的理由
- ✗ 发现问题不说、按原样继续
- ✗ 没有测试安全网就重构
- ✗ 重构和业务改动混在一个提交里
- ✗ 借"顺手重构"之名改任务边界外的东西
- ✗ 铲一半留下新旧两套模式并存
- ✗ 登记了债务就当还完了（登记不是还债，是标记）
- ✗ 债务表无限增长而不安排偿还
