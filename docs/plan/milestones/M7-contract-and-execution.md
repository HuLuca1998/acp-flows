# M7 · 它按契约干活，我看得见管得住

> ★ 施工图在快做到时才建（`roadmap.md` 的规矩）。本文件 2026-08-09 建于 `M6` 主体完成之后。

## 目标

**每个单元开工前先冻一份契约：这次要做什么、允许改哪些文件、凭什么说做完了。
然后实现工程师在那个边界里干活——而与你对话的那条会话始终只读。**

★★ 契约的**写入边界**是这一步真正的产物。没有它，「AI 要动文件」这件事
只能靠用户逐条判断；有了它，越界的那一次会被标出来——
而用户要的正是「它有没有动不该动的东西」。

## 完成标志

用户自己做这八件事，全部成功：

1. 单元开始前 → **`Claude · 单元设计师`** 产出契约 `v1`，可查看全文
2. 契约冻结后不能改；要改就出 `v2`，旧版留着
3. 干活时每条消息显示**注入了什么**：`skill:xxx@版本 · mem-xxx`
4. AI 要动文件 → 权限卡片，**标出是否在写入边界内**（边界来自契约）
5. 点「停」→ AI 真的停，现场保留
6. 本轮结束显示「本轮小结」四行（计划变更 / 契约 / 注入清单 / 处理方式）
7. ★★ **实现工程师是另一条会话**——它写文件，而与你对话的那条始终只读
8. ★★ 一个单元跑好几轮时，实现会话**也是同一条**（记得自己刚改过什么）

1. 写入边界要用**正则**而不是路径前缀 —— 停下来问（正则会让用户写出
   自己都读不懂的边界，而边界是他唯一的防线）
2. 需要让实现工程师**自己**决定边界 —— 那等于没有边界
3. 注入清单要靠解析 AI 的自由文本 —— 参照 `U6.2.1` 的裁定处理

## S7.1 · 契约的写入边界

### ◐ U7.1.1 · 契约带上写入边界

| | |
|---|---|
| `goal` | 契约里写明「允许改哪些、禁止改哪些」，冻结后不可变 |
| `allowed_changes` | `backend/internal/domain/model/unit_contract.go` |
| `forbidden_changes` | 用正则表达边界（见停止条件）；边界允许为空 |
| `stop_conditions` | 路径前缀表达不了某个真实的边界需求 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 边界用**路径前缀**，不是正则 | 断言 `internal/acp/` 匹配它下面的文件，不匹配 `internal/acpx/` |
| R2 | 禁止项**压过**允许项 | 断言同时命中时判为越界——安全默认是「不许」 |
| R3 | 边界为空时**一律判越界** | 断言没有边界就没有放行，而不是全放行 |
| R4 | 冻结后边界不可变 | 断言改边界返回 `ErrContractFrozen` |
| R5 | 越界判定不看文件存不存在 | 断言对一个还不存在的路径也判得出来 |

### ◐ U7.1.2 · 契约落库与版本链

| | |
|---|---|
| `goal` | 契约存得下读得回，旧版一个字不改 |
| `allowed_changes` | `backend/internal/store/**` |
| `forbidden_changes` | 仓储出现 Update/Delete；旧版被覆盖 |
| `stop_conditions` | 契约全文（YAML）在关系表里表达不了 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 存进去再取出来，边界与标准都在 | 断言逐字相同 |
| R2 | 改写已冻结的版本被拒 | 断言库里那条一个字没变 |
| R3 | 版本链从新到旧 | 断言顺序 |
| R4 | 仓储没有改写类方法 | 反射断言 |

## S7.2 · 权限裁决对上边界

### ◐ U7.2.1 · 权限卡片标出「边界内 / 边界外」

| | |
|---|---|
| `goal` | AI 要动文件时，用户一眼看出它有没有越界 |
| `allowed_changes` | `backend/internal/app/permission/**` · `api/openapi.yaml` · `frontend/src/features/permission/**` |
| `forbidden_changes` | 越界时自动拒绝（那是用户的决定）；边界读不到时**默认放行** |
| `stop_conditions` | 权限请求里拿不到具体路径 —— 那时标不出边界内外 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 边界内的请求标 `in_boundary` | 断言载荷字段 |
| R2 | 越界的请求标 `out_of_boundary`，界面**显眼** | 断言载荷 + 界面有区分 |
| R3 | 读不到契约时标 `unknown`，**不是** `in_boundary` | 断言不知道就说不知道 |
| R4 | 标记不改变裁决权 | 断言越界也照样交给用户选 |
| R5 | 能切英文 | 断言无硬编码中文 |

**R1 R3 R4 做完了，且接到真实数据上**：`Work.CurrentUnitID` → 那个单元的
契约 → `Judge(path)`。四种「说不清」（没装配 / 工作查不到 / 还没开始做单元 /
没有路径）都返回 `unknown`。

★★ 判定**不改变裁决权**（R4）：越界照样交给用户选。自动拒绝的话，
用户会发现「明明是我让它改的，它却不改」——而边界是**提示**，不是闸门。

★ 原来那个字段是 `OutOfBounds bool`，它**表达不了「不知道」**——
用 bool 的话，契约没冻结时那条请求会长得和「边界内」一模一样，
而那正是用户最需要看清楚 AI 要动什么的时刻。改成三态。

★ 界面（R2 R5）跟着 `U7.3.1` 一起做：现在做的话，界面上会有一个
永远显示 `unknown` 的标记，比不显示更让人困惑。

## S7.3 · 实现工程师干活

### ◐ U7.3.1 · 单元开工：契约冻结后交给实现工程师

| | |
|---|---|
| `goal` | 契约冻结 → 实现工程师在另一条会话里干活 |
| `allowed_changes` | `backend/internal/app/work/**` · `backend/internal/api/**` |
| `forbidden_changes` | 契约没冻结就开工；实现轮与对话轮共用一条会话 |
| `stop_conditions` | 单元的角色与契约的执行者对不上 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 契约**没冻结**时拒绝开工 | 断言报错且错误码可判定 |
| R2 | 实现轮的角色是**单元自己派的那个** | 断言 `RoleID` 来自 `Unit.RoleID()` |
| R3 | 实现会话与对话会话**不是同一条** | 断言两者 sessionId 不同 |
| R4 | 同一个单元跑两轮，会话**是同一条** | 断言 `session/new` 只发一次 |
| R5 | 实现轮的 prompt 里带着契约全文 | 断言 prompt 含验收标准与边界 |

**R1 R2 R5 已完成。** R3 R4（两条会话的分与合）由会话池按「工作 + 角色」
分键**天然成立**（`U5.1.1` `U5.1.2` 已验），这里没有新代码，
所以也没有新断言——**要验得等真机**。

★★ 顺带补了一条状态迁移：**计划落库了就是 `ready`**。不推的话工作停在
`planning`，而 `StartUnit` 要求 ready——用户会看到「计划出来了但点不动
开始」，而没有任何地方说明为什么。

★ 写测试时撞上状态机拦住 `clarifying → executing`，**那条限制是对的**：
绕过它等于让测试跑在一条真实路径产生不了的状态上（这个项目已经七次栽在
「测试构造了真实路径产生不了的输入」）。所以测试改成走完整流程：
冻结需求 → 规划 → 落计划 → 开工。
