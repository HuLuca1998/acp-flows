# M10 · 它越用越懂我的项目

> ★ 施工图在快做到时才建（`roadmap.md` 的规矩）。本文件 2026-08-10 建于 `M9` 完成之后。

## 目标

**干活时冒出来的经验，用户点一下就进了记忆库；下一轮它带着这些经验开工。**

★★ 这一步是 Duet 与「每次从零开始的 AI」的分界线。而它的底线是
**记忆由用户收下，不由 AI 自己写进去**——AI 自己写的话，
一条它误解的「经验」会一直影响后面每一轮，而用户从没同意过。

## 完成标志

用户自己做这五件事，全部成功：

1. 干活中冒出经验 → 消息里出现「**记忆候选**：… · 审核」

> 实操：真机 `work-03` `work-04` 跑通了整条链路，但**没等到 AI 自己提一条**——
> 两轮都是在一个空项目里做澄清，它确实没有值得记的经验（提示词明写
> 「没有就不要输出」，这正是它该有的表现）。链路本身有守卫顶着：
> `TestAgentTurn_SystemPromptTellsAgentHowToProposeMemory` 断的是真的传给
> Agent 的 SystemPrompt，拆掉 `role.go` 那行拼接它立刻红。
> **欠一次在真实开发单元里的观察**，那才是它该冒经验的场景。

2. 点「审核」→ 决定收不收；收了进记忆库

> 实操：**欠**。记忆页的「收下 / 不要」在 `U2.3.1` 就有了，但候选是从
> 时间线上点进去的那条路径还没接——第 1 条没等到真候选，这条也就没验成。

3. 记忆页：按项目 / 跨项目分组，按 `active / 候选 / 已失效` 筛选，有类型

> 实操：`U2.3.1` 完成时验过，四档筛选与分组都在。

4. Skill 页：带**版本号**、**命中计数**、**校验态**（draft 说明为什么没过）

> 实操：版本号与校验态在 `U2.2.1` 验过（真目录真文件扫出来）。
> 命中计数由 `U10.4.1` 补齐：`skill_hits` 表 + 注入接线 + API 填值 +
> 界面那一列。**欠一次真机核对**（起服务、放一个 active skill、
> 跑一轮、看那个数字从 0 变 1）。

5. 下一轮对话的**注入行**里，能看到刚收的那条记忆

> 实操：真机 `work-04` 与 `work-05`。往记忆库放一条 active 记忆并入库，
> 起一个工作后查库：`injection` 事件的载荷是
> `{"count":1,"memory_ids":["mem-real-01"]}`，`memories.hit_count` 从 0 变成 1。
> 计数是**应用自己数的**——那两轮 AI 的回复里一个字都没提这条记忆。
> `work-05` 里那条记忆还进了本轮小结，与 `injection` 事件同源。

## 全局停止条件

1. 记忆**正文**要塞进数据库 —— 那违反 INV-MEM-8（正文只在 md 文件里，
   用户要能用任何编辑器改它）
2. AI 可以**自己**把记忆写成 active —— 那是这一步的底线
3. 命中计数要靠 AI 自报 —— 应用自己数（与 `M8` 的证据同理）

## S10.4 · Skill 的命中计数

> ★ 这个单元是**真机核对逼出来的**：完成标志第 4 条要求 Skill 页显示
> 命中计数，而 `hit_count` 只加在了 `memories` 表上——`skills` 那边是空的。
> 单元测试全绿，因为没有一条测试问过「Skill 的计数在哪」。

### ✓ U10.4.1 · Skill 页显示命中计数

| | |
|---|---|
| `goal` | 每个 Skill 显示被注入过几次，数字由应用数 |
| `allowed_changes` | `backend/internal/store/**` · `backend/internal/app/work/**` · `frontend/src/features/skill/**` |
| `forbidden_changes` | 计数由 AI 自报；把「扫到了」算成「用过了」 |
| `stop_conditions` | Skill 的注入还没接线 —— 那时计数没有可数的东西，先接注入 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 注入一次计数加一 | 断言两轮之后是 2 |
| R2 | 计数**由应用数**，不问 AI | 断言 AI 回复里胡说也不影响数字 |
| R3 | 只有 active 的 Skill 才计数 | 断言 draft 的数字不动 |
| R4 | 从没用过显示 `0`，不是空白 | 断言默认值是 0 而不是 NULL |
| R5 | 能切英文 | 断言无硬编码中文 |

**做完了。** 后端补的是**正文端点**：`GET /v1/memories/{id}/body`。

★★ 原来 `memoryBody` 上写着「没有正文字段（INV-MEM-8）」——那把两件事
混了：INV-MEM-8 说的是正文**不进数据库**，不是 API 不能给。
用户要读到正文才决定得了收不收，不给他就是在盲选。

★ 正文单独一个端点而不是塞进列表：列表里逐条读文件是 N 次磁盘 IO，
而记忆页一屏能列几十条。

★ 前端这一步顺带给事件注册表加了 `refFrom`：一段有没有 id、点不点得动，
**写在注册表里**而不是在渲染层挖载荷——加一类可操作事件仍然只加一条记录。
**R1 R2 R3 做完了，且接到真实路径上**：`SetSkills(skillstore.Store{...},
db.SkillHits())`，两处 `RunTurn` 的 prompt 都过 `applyInjection`。

★★ 做的时候发现 **Skill 压根没被注入过**——stop_conditions 里写的
「注入还没接线，先接注入」正好撞上。所以这个单元做的是两件事：
先让 active 的 Skill 真的进 prompt，再数它。

★ `skill_hits` 是**单独一张表**：没有 `skills` 表——Skill 是扫盘产物，
用户可以随时增删改，我们不留副本（与记忆正文同理）。这里只存
我们自己观察到的一件事：它被注入过几次。

★★ R4 补的是一个**契约里早就有、真实路径上永远是 0** 的字段：
`hit_count` 在 `openapi.yaml` 里躺着，而 handler 从没填过它，
响应结构体上还挂着 `omitempty`——**0 会被吃掉**，而界面上
「从没用过」正是要显示那个 0。这类缺陷最难发现：字段在、类型对、
测试全绿，只是那个数字永远不动。
