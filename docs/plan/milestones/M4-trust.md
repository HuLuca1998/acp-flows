# M4 · 值得信任

> 对应验收点 **V9 · V10 · V11 · V12**（[`../acceptance.md`](../acceptance.md)）。

## 目标

**关掉再打开工作还在；用户看得到计划怎么来的、凭什么说做完了；重要决定会等他拍板。**

## 完成标志

用户自己做这四件事，全部成功：

1. 做到一半关掉 Duet 再打开 → 对话、计划、进度都在，**AI 还记得之前聊了什么**
2. 点「查看计划」→ 看得到拆成几块、改过几版、每次为什么改
3. 点「打开证据」→ 看得到改了哪些文件、跑了哪些测试、结果是什么
4. 遇到重要岔路 → AI 停下来给选项和推荐，等他选

## 全局停止条件

1. 恢复失败时**伪造「会话仍连续」**——宁可显式降级为新会话
2. 证据由 AI 转述而非应用直接采集
3. 计划被改写而不是新增版本
4. 撞上 [`../open-questions.md`](../open-questions.md) 未决项

## S4.1 · 关掉再打开，工作还在

### ○ U4.1.1 · 会话恢复与游标持久化

| | |
|---|---|
| `goal` | 重启后能接着上次继续，AI 记得前文 |
| `allowed_changes` | `backend/internal/acp/session/**` · `backend/internal/store/**` |
| `forbidden_changes` | 恢复失败时假装成功 |
| `stop_conditions` | Fake 无法模拟历史回放 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 恢复后新一轮能延续上下文 | Fake 记住暗号 → 重建会话 → 断言能复述 |
| R2 | **会话标识端到端穿透**，第 2 轮记得第 1 轮 | 断言两轮落在同一个会话标识上 |
| R3 | 恢复失败时**显式标记为新会话** | 断言降级路径被走到且用户可见 |
| R4 | 事件游标跨重启连续 | 断言重启后序号不回退不重复 |

> R2 是前一个项目最严重的一条错误：会话标识在某一层丢了，
> 表现为「第 2 轮不记得第 1 轮」，而界面上看着完全正常。

### ○ U4.1.2 · 检查点与启动时恢复

| | |
|---|---|
| `goal` | 用户重启应用后能看到「有哪些工作可以接着做」并一键恢复 |
| `allowed_changes` | `backend/internal/app/checkpoint/**` · `backend/internal/api/**` 的 `/v1/system/resume` · `frontend/src/features/work/**` |
| `forbidden_changes` | 恢复时覆盖用户在此期间的手工改动 |
| `stop_conditions` | 检查点内容与工作区实际状态冲突 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 可恢复的工作被列出 | 断言列表含工作标识与暂停时间 |
| R2 | 恢复后状态回到暂停前 | 断言状态与事件游标都对得上 |
| R3 | 工作区被手工改动过时**先告知再恢复** | 断言出现冲突提示而不是静默覆盖 |
| R4 | **这条打通 M1 的完整一键更新** | 断言更新前暂停 → 更新后恢复的全流程可跑通 |

## S4.2 · 看得到计划

### ○ U4.2.1 · 计划只增不改与重规划记录

| | |
|---|---|
| `goal` | 用户能看到计划改过几版、每次为什么改、已验收的工作怎么处置 |
| `allowed_changes` | `backend/internal/domain/model/{plan,unit_contract}.go` 及其测试 |
| `forbidden_changes` | `domain` import 任何内部包；出现 `context.Context` 或 `time.Now()` |
| `stop_conditions` | 撞上未决项：验收标准是否属于契约字段、谁产出契约 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | **不存在任何修改已有计划版本的方法** | 反射断言：导出方法都不改已冻结版本的字段 |
| R2 | 重规划必须声明已验收工作的处置（四选一） | 缺处置时断言明确错误 |
| R3 | 契约冻结后改字段返回错误 | 断言冻结错误 |
| R4 | 契约版本号严格递增 | 断言 v3 之后只能是 v4 |
| R5 | 覆盖率 ≥ 90% | `make cover` |

### ○ U4.2.2 · 计划面板界面

| `forbidden_changes` | 硬编码文案与样式 |
| `stop_conditions` | 设计稿里找不到对应条目 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 子计划与单元按设计稿层级展示 | 断言层级结构与设计稿一致 |
| R2 | 重规划记录可展开，每条有原因 | 断言每个版本都带一句原因 |

## S4.3 · 看得到证据

### ○ U4.3.1 · 应用直接采集证据

| | |
|---|---|
| `goal` | 「做完了」有据可查，而且证据不是 AI 说的，是应用自己采的 |
| `allowed_changes` | `backend/internal/app/evidence/**` · `backend/internal/gitx/**` |
| `forbidden_changes` | **把 Agent 的自述当证据** |
| `stop_conditions` | 某类证据无法由应用直接采集 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 改动 diff 由应用从工作区直接读 | 断言 diff 内容与 git 实际输出一致 |
| R2 | 命令的退出码与输出被原样记录 | 断言退出码非 0 时证据标记为失败 |
| R3 | 每条验收标准能对应到证据 | 断言无证据的标准被标为「未验证」 |
| R4 | **AI 声称通过但无证据时判为未通过** | 断言这种情况不被计入已验收 |

### ○ U4.3.2 · 证据抽屉界面

| | |
|---|---|
| `goal` | 用户点开就能看到改了什么、测了什么、结果如何 |
| `allowed_changes` | `frontend/src/features/evidence/**` |
| `forbidden_changes` | 硬编码文案与样式 |
| `stop_conditions` | 设计稿里找不到对应条目 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | diff 可读且区分增删 | 断言增删行有不同的视觉标记 |
| R2 | 命令输出可展开，退出码可见 | 断言退出码被展示 |
| R3 | 无证据的标准显式标注 | 断言出现「无证据」而不是留空 |

## S4.4 · 重要决定等我拍板

### ○ U4.4.1 · 决策等级与阻塞

| | |
|---|---|
| `goal` | 该问的问、不该问的别烦用户 |
| `allowed_changes` | `backend/internal/domain/policy/**` · `backend/internal/app/decision/**` |
| `forbidden_changes` | 无法判定等级时擅自放行（应上调等级） |
| `stop_conditions` | 撞上未决项：某个场景的等级判定无先例 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 等级判定有穷举测试 | 每个等级至少一个用例 |
| R2 | 无法判定时**上调**而不是放行 | 断言未知场景被判为需要用户确认 |
| R3 | 需要拍板时工作进入等待态 | 断言状态变为 `waiting_user` |
| R4 | 用户选完之后工作继续 | 断言状态离开等待态 |

### ○ U4.4.2 · 决策卡片界面

| | |
|---|---|
| `goal` | 用户看得懂在问什么、每个选项什么后果、推荐哪个 |
| `allowed_changes` | `frontend/src/features/decision/**` |
| `forbidden_changes` | 硬编码文案；把技术错误原文直接甩给用户 |
| `stop_conditions` | 设计稿里找不到对应条目 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 选项与后果成对展示，推荐项有标记 | 断言推荐项唯一且有视觉区分 |
| R2 | 未决策时工作明确显示为等待中 | 断言状态词等宽显示 |
| R3 | 决策历史可回溯 | 断言选过的决策能查到当时的选项 |
