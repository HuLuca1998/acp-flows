# M8 · 它说做完了，我能验

> ★ 施工图在快做到时才建（`roadmap.md` 的规矩）。本文件 2026-08-09 建于 `M7` 主体完成之后。

## 目标

**AI 说做完了，用户能一条条核对——而核对用的证据是应用自己采集的，
不是 AI 转述的。**

★★ 这一步的全部意义在第 4 条：**证据由应用直接采集**。让 AI 报告自己
干了什么，等于让被考核的人填自己的考勤表——它不需要撒谎，只需要
「记错了」一次，用户就再也不知道该信哪一条。

## 完成标志

用户自己做这五件事，全部成功：

1. 单元跑完 → 看到「验收证据 N 条 / 标准 M 条」
2. 点开证据 → **四类**：Git diff · 测试输出 · 命令记录 · 审查意见
3. 每条验收标准旁边标 `✓ ev-441` 或 `○ 无证据`
4. ★★ 证据是**应用直接采集的**，不是 AI 转述的
5. 验收通过 → 自动提交到工作分支 + 落检查点（`ck-07 · abc123`）

## 全局停止条件

1. 某一类证据只能靠 AI 转述（拿不到原始输出）—— 停下来问，
   **不要把转述当证据存**
2. 自动提交会覆盖用户在工作区里的手工改动 —— 停下来问
3. 「验收通过」需要 AI 自己判断 —— 那是用户的决定

## S8.1 · 证据

### ◐ U8.1.1 · 证据进 domain

| | |
|---|---|
| `goal` | 一条证据知道自己是哪一类、从哪来、对应哪条标准 |
| `allowed_changes` | `backend/internal/domain/model/**` |
| `forbidden_changes` | 证据可被改写（那就不是证据了）；来源允许留空 |
| `stop_conditions` | 四类之外还需要第五类 —— 先确认它不是前四类的变体 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 四类封闭：diff / 测试 / 命令 / 审查 | 断言第五类被拒 |
| R2 | 证据**不可变** | 反射断言没有指针接收者的导出 mutator |
| R3 | 每条证据记着**谁采集的** | 断言 `collected_by` 必填，且区分「应用」与「AI」 |
| R4 | AI 转述的证据**标出来** | 断言它与应用采集的在类型上分得开 |
| R5 | 一条证据可以对应多条标准，反之亦然 | 断言多对多关系表达得出来 |

### ◐ U8.1.2 · 应用直接采集 diff 与命令记录

| | |
|---|---|
| `goal` | 单元跑完，应用自己去读 git diff 与命令输出 |
| `allowed_changes` | `backend/internal/gitx/**` · `backend/internal/app/work/**` |
| `forbidden_changes` | 把 AI 说的话存成证据；采集失败时编一条空证据 |
| `stop_conditions` | 命令记录拿不到原始输出 —— 见全局停止条件 1 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | diff 来自 `git`，逐文件带增删行数 | 断言与真仓库的实际改动一致 |
| R2 | 采集**只读**，不动工作区 | 断言采集前后工作区快照一致 |
| R3 | 采集失败时**说出来**，不留空证据 | 断言报错且事件里有原因 |
| R4 | 采集的证据标着 `collected_by=app` | 断言来源 |

**R1–R4 已完成。**

★★ 采集时**发现一个真 bug**：`git diff --numstat` **不含未跟踪的新文件**，
而 AI 干活时新建文件是常态。不算的话，一个新写了三个文件的单元，
右栏与验收证据都显示「改了 0 个文件」——用户会以为它什么都没做。
修在 `gitx.ProbeWorktree`（`ls-files --others --exclude-standard`，
被 `.gitignore` 忽略的不算，否则 `node_modules` 会把证据淹掉）。

## S8.2 · 验收

### ◐ U8.2.1 · 标准与证据对照

| | |
|---|---|
| `goal` | 每条验收标准旁边看得到「有没有证据」 |
| `allowed_changes` | `backend/internal/app/work/**` · `api/openapi.yaml` |
| `forbidden_changes` | 没有证据的标准显示成通过；证据数当成通过数 |
| `stop_conditions` | 标准与证据的对应关系要靠 AI 判断 —— 停下来问 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 有证据的标准标 `✓ ev-441` | 断言证据 id 出现在那条标准上 |
| R2 | 没证据的标 `○ 无证据`，**不是通过** | 断言它与通过分得开 |
| R3 | 「N 条证据 / M 条标准」两个数各自算 | 断言证据多于标准时不显示成「超额通过」 |
| R4 | 一条证据对应多条标准时**各自都标上** | 断言不只标第一条 |

**R1–R3 已完成**（后端 `AcceptanceOf` + `/acceptance` 端点 + 界面）。
R4 由 `CriteriaCoverage` 的多对多保证，domain 层有断言。

★ 界面上 **AI 转述的证据单独标出来**（`AI 转述，未经核实`）——
不标的话一条转述会和一份真 diff 长得一样，而用户判断「该不该信」
全靠这一点。应用采集的**不标**：大多数证据都是它，标了反而没人看。

### ◐ U8.2.2 · 验收通过 → 自动提交 + 检查点

| | |
|---|---|
| `goal` | 用户点「通过」，改动落成一个 commit，并留一个可恢复点 |
| `allowed_changes` | `backend/internal/app/work/**` · `backend/internal/gitx/**` |
| `forbidden_changes` | AI 自己判断通过；提交时带上用户的手工改动而不说明 |
| `stop_conditions` | 工作区有用户手工改动 —— 见全局停止条件 2 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 通过**由用户点**，不是 AI 判断 | 断言没有自动通过的路径 |
| R2 | 提交发生在**工作分支**上 | 断言用户的分支一字不动 |
| R3 | 提交信息里带单元 id 与契约版本 | 断言 commit message |
| R4 | 落一个检查点，绑着那个 commit | 断言检查点能查到 sha |
| R5 | 没有改动时**不空提交** | 断言零改动时明确说明而不是造一个空 commit |

**R1–R5 已完成。**

★★ 多加了一条 R1 没写但同样要紧的：**一条标准都没有证据时拒绝通过**。
允许的话，「验收」这个动作就没有内容了——用户点通过时以为自己核对过什么，
而实际上什么都没有。

★ 采集时发现 `git diff` 不含未跟踪文件（见 `U8.1.2`），提交这边用
`git add -A` 带上它们——不然提交里少了一半东西，而 diff 证据里明明有。

## S8.3 · 接着做的入口

> ★★ 探索发现的**功能级缺口**：检查点、`GET /v1/system/resume`、恢复逻辑
> 后端全做完了（旧 `U4.1.*` 与 `M8`），而**界面上没有任何入口**。
> 用户打开应用永远看不到「有 2 个工作可以接着做」——那整套代码等于没用。

### ✓ U8.3.1 · 启动时列出「能接着做的」

| | |
|---|---|
| `goal` | 打开应用就能看到哪些工作能接着做，点一下回到现场 |
| `allowed_changes` | `frontend/src/features/resume/**` · `frontend/src/app/**` |
| `forbidden_changes` | 自动恢复（那是用户的决定）；工作区脏时静默覆盖 |
| `stop_conditions` | 恢复之后该落在哪一屏说不清 —— 那时停下来问 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 列表显示**停在哪个单元**与暂停时间 | 断言两者都在 DOM 里 |
| R2 | 一个都没有时**整块不显示** | 断言不出现空列表标题 |
| R3 | 工作区脏时**先告知**，不静默恢复 | 断言有提示且不自动继续 |
| R4 | 点一下回到那个工作的对话页 | 断言路由跳转 |
| R5 | 能切英文 | 断言无硬编码中文 |

★ R1 里那两个字段后端刚补齐（`unit_id` 从没被填过，见
`check-unfilled-fields.sh`）——不显示的话，用户看到的是一串
`work-03 · work-05`，那两个词对他没有任何意义。

**R1 R2 R4 R5 做完了。** 入口排在主区**最上面**：往下滚才发现的话，
他多半已经开了个新工作。点一条走 `open` 意图，与左栏点已有工作
**同一条路**——另写一条的话两处行为迟早分叉。

★★ **不自动恢复**：接着做是用户的决定。自动跳进去的话，他打开应用
想开个新工作，却发现自己落在昨天那个半截的现场里。

★ 做完之后 `check-endpoint-reach.sh` 的清单里 `GET /v1/system/resume`
消失了——那道检查确实在跟踪真实状态，不是一次性的报告。

**R3 也做完了。** 做的过程中发现自己的第一版**不完整**：卡片只是跳到
对话页，没有调用真正的 `Resume`——界面看起来能用，而切 worktree 与
脏检查那一整套从没跑过。

★★ 根因是**后端有 `Resume` 但没有 HTTP 端点**：只有 `GET` 列表。
补了 `POST /v1/system/resume/{id}`，脏时回 **409 而不是 500**——
脏是一个用户能处理的状态，500 只会显示成「出错了」。

★★ 脏时**问一句再继续**，两个按钮同等分量：继续与算了都是正当的选择。
恢复失败（不是脏）时**不跳**——跳过去他会对着一个没恢复的工作接着说话。
