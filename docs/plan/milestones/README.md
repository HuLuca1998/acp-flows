# 里程碑体系

> **里程碑是「用户能体验的一件事」，不是「技术做完的一层」。**
>
> 2026-08-07 重建：原来按技术分层划分（M0「地基：ACP 协议层」之类），
> 使用者根本无法观测，等于没有里程碑。现在每个里程碑都是一组
> **他能自己动手试、自己判断成没成**的功能。

用户视角的验收标准在 [`../acceptance.md`](../acceptance.md)（V1–V15）——
**那份是目的，本目录是施工图。**

---

## 六步流程 ★

每个单元都要走完这六步，**一步都不能跳**：

```
① 里程碑        这个单元属于哪个用户功能（必须能指到 V几）
② 拆分单元      写全五段契约：goal / allowed / forbidden / 验收标准 / stop
③ 单元实现计划   动手前写下：改哪些文件、什么顺序、怎么验
④ 单元测试（代码）★ 先写会失败的测试，跑一次确认是红的，再写实现
⑤ 操作测试（UI）★ 把应用真的跑起来，以用户视角点一遍
⑥ 通知用户测试   ⑤ 全过之后才告诉用户「V几 可以验收了」
```

### 第 ④ 步：单元测试

铁律 1。详见 [`../../rules/testing-strategy.md`](../../rules/testing-strategy.md)。
**先红过**的测试才算数，提交信息里要写出它的名字。

### 第 ⑤ 步：操作测试 ★ 最容易被跳过的一步

**「测试全绿」不等于「功能能用」。** 单测证明代码逻辑对，
证明不了按钮点得动、文案看得懂、报错看得明白、流程走得通。

必做：

| 做什么 | 怎么做 |
|---|---|
| 把应用跑起来 | `make dev`（用完 `make dev-stop`），或装好的 `.app` |
| 照着用户会做的操作走一遍 | 对照 `acceptance.md` 里那条 V 的「你怎么试」 |
| 逐条核对现象 | 对照「应该看到什么」，**包括文案是否与设计稿一致** |
| 把失败路径也试掉 | 对照「常见的做错的样子」——那些是看着像做完了其实没有的情况 |
| 留证据 | 截图 / 页面文本 / 真实响应。不是「我认为应该可以」 |

**有一条对不上就不要进第 ⑥ 步。**

### 第 ⑥ 步：通知用户

一句话说清「V几 可以验收了」+ 怎么试 + 你自己验到了什么。
**不要把测试压力转嫁给用户**——他是来验收产品的，不是来当测试员的。

## 里程碑清单

| 里程碑 | 用户拿到什么 | 覆盖验收点 |
|---|---|---|
| [M1 · 装得上，能一直更新](M1-install-and-update.md) | 能装、能开、以后每次改动都靠一键更新拿到 | V1 V2 V3 |
| [M2 · 能提需求，看得见 AI 在干什么](M2-talk-and-observe.md) | 加项目、提需求、AI 边做边显示 | V4 V5 V6 |
| [M3 · 能管住 AI](M3-control.md) | 动文件前先问我、随时能喊停且现场保留 | V7 V8 |
| [M4 · 值得信任](M4-trust.md) | 关掉能恢复、看得到计划与证据、重要决定等我拍板 | V9 V10 V11 V12 |

**顺序是被用户价值决定的**，不是被技术依赖决定的：
M1 排第一是因为没有一键更新的话，用户每次验收发现问题都要卸载重装。

## 编号规则

```
M<里程碑>                 M1
S<里程碑>.<子计划>         S1.2
U<里程碑>.<子计划>.<单元>   U1.2.3
```

编号**只增不复用**。单元合并或废弃时保留编号并标注。
分支名直接用编号：`feat/acp-u1-2-3-updater-ui`。

> **2026-08-07 之前的编号（U0.x）已废弃。** 那套按技术分层编的号
> 在本次重建中被吸收进各功能里程碑。已完成的工作见各里程碑的「已经就绪的地基」。

## 每个单元必须写全五段

| 段 | 内容 | 省了会怎样 |
|---|---|---|
| `goal` | 一句话，做完之后**用户**能多做什么 | 做着做着跑偏成技术自嗨 |
| `allowed_changes` | 允许改的文件/目录，具体到路径 | 边界形同虚设 |
| `forbidden_changes` | 明确禁止碰的东西 | 「顺手改一下」 |
| `acceptance_criteria` | 逐条，每条能变成一句可执行断言 | 无法测试先行 |
| `stop_conditions` | 什么情况必须停下来上报 | AI 自行扩大范围 |

**写不出可断言的验收标准 = 这个单元还没想清楚。** 回去拆。

`make check-milestones` 会逐条校验这五段与断言是否齐备。

## 状态标记

| 标记 | 含义 |
|---|---|
| `○` | 未开始 |
| `◐` | 进行中（标注分支名） |
| `✓` | 六步全走完（**标注提交号**） |
| `⊘` | 已废弃（**必须写原因**） |

★ **`✓` 的含义是六步全走完，不是「代码写完了」。**
第 ⑤ 步操作测试没做的单元一律只能标 `◐`。

## 什么时候改这些文档

| 情况 | 动作 |
|---|---|
| 单元做完（六步） | 就地标 `✓` + 提交号 |
| 发现单元拆错了 | **加新单元，不改已验收的** |
| 发现整个里程碑的假设错了 | 停下来找人 |
| 验收标准写不出断言 | 说明没想清楚，回去拆细 |

**不要在这里写实现细节。** 单元只说「做什么、边界在哪、怎么算完」，
「怎么做」在 [`../../spec/`](../../spec/) 的专题文档里。
