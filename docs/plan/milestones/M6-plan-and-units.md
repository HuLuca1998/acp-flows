# M6 · 它给出计划，每条都派好了人

> ★ 施工图在快做到时才建（`roadmap.md` 的规矩）。本文件 2026-08-09 建于 `M5` 主体完成之后。

## 目标

**需求冻结之后，计划架构师把它拆成子计划与单元，
而每个单元都写明由哪个角色做——写一个不存在的角色，当场报错。**

★★ 裁定三：**每个单元都要分配角色**。不分配的后果是到执行时才发现没人认领，
而那时用户已经等了几分钟；更糟的是随便派一个，让实现方审查自己的产出
（INV-ATT-8 明令禁止）。

## 完成标志

用户自己做这七件事，全部成功：

1. 需求冻结后 → **`Claude · 计划架构师`** 产出 `plan v1`，标「N 子计划 · M 单元」
   > 实操：2026-08-09 `~/.duet-dev` 真 claude。冻结需求 → `POST /works/work-01/plan`
   > → 事件流里 `role=plan_architect`，产出
   > `{"version":1,"subplans":4,"units":12,"title":"给取消功能补一份使用文档…"}`
2. 计划面板看到**子计划 DAG**：每个子计划的状态与进度（`accepted · 3/3`）
   > 实操：`GET /works/work-01/plan` 返回四个子计划，各带 `status` 与 `done/total`
   > （`subplan-01 摸清取消的真实现状 · pending · 0/3`）
3. 每个子计划下挂**单元**，带状态与依赖（`依赖 unit-012 · 契约未冻结`）
   > 实操：`unit-004 · decision_advisor · depends_on=[unit-001]`，
   > `unit-005` 依赖两个（`unit-003` `unit-004`）——跨子计划的依赖也对
4. 看到**变更历史**：改过几版、每次为什么改
   > 实操：`GET /works/work-01/plan/history` 返回 `versions` 数组。
   > ★ 只有一版时界面不显示这一块（「历史」只有一条等于没有历史）
5. 重规划时**必须声明**已验收工作的处置（仍有效 / 需补充 / 需回滚 / 已废弃）
   > 实操：**没走到**——要有一个已验收的单元才谈得上重规划，那是 `M8`。
   > 领域层的强制已经在（`TestPlan_R4_ReplanNeedsDispositions`），真机欠着
6. ★★ **每个单元都标着由哪个角色做**（裁定三）
   > 实操：`SELECT count(*) FROM units WHERE role_id=''` → **0**。
   > 十二个单元全派了人（implementer / unit_designer / decision_advisor…）
7. ★★ 分配的角色**必须是角色库里存在的**
   > 实操：真 AI 这次派的都是真角色。**假角色的路径由解析层挡着**
   > （`TestParsePlanReply_UnknownRoleIsRejected`）——真机没构造出这一场景，
   > 因为 prompt 里把八个角色 id 逐个列了出来

## ★★ 真机撞到的：计划架构师会**申请切出只读档**

规划轮跑到最后，claude 调 `ExitPlanMode`，触发一条 `switch_mode` 权限请求，
挂在那里等应答。**没人应答的话规划轮永远不结束**——用户看到的是
「正在规划」然后没有下文。

这次手工应答 `plan`（「不，继续规划」）之后它立刻输出了计划 JSON。

★ 这说明两件事：
1. 只读档**确实在生效**（它想写东西，得先申请）
2. 界面上必须有人能应答这条请求 —— 权限卡片已经有了（`U3.1.3`），
   但**计划轮的权限请求还没接到那张卡上**。归 `M7` 的 `U7.2.1`

## S6.1 · 计划的结构

### ◐ U6.1.1 · 子计划与单元进 domain

| | |
|---|---|
| `goal` | 一版计划装得下「N 个子计划、M 个单元」，每个单元写明角色 |
| `allowed_changes` | `backend/internal/domain/model/plan.go` · 同目录新文件 |
| `forbidden_changes` | 单元的角色允许留空（裁定三反对）；在旧版本上追加单元 |
| `stop_conditions` | 单元依赖出现环，而规格没说该怎么办 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 单元**必须**有角色，且角色要在角色库里 | 断言不存在的角色被拒，错误里带角色 id |
| R2 | 计划仍然**不可变** | 反射断言没有指针接收者的导出 mutator |
| R3 | 依赖必须指向**同一版计划里存在的**单元 | 断言指向不存在的单元被拒 |
| R4 | 依赖**不成环** | 造一个 A→B→A，断言被拒且错误里列出环 |
| R5 | 子计划的进度由单元算出来，不单独存 | 断言 `3/3` 来自单元状态，不是一个字段 |

### ◐ U6.1.2 · 计划落库与版本链

| | |
|---|---|
| `goal` | 计划存得下、读得回，旧版本一个字不改 |
| `allowed_changes` | `backend/internal/store/**` |
| `forbidden_changes` | 仓储出现 Update/Delete 类方法；旧版本被覆盖 |
| `stop_conditions` | 子计划 DAG 在关系型表里表达不了 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 存进去再取出来，DAG 结构完整 | 断言子计划、单元、依赖、角色都还原 |
| R2 | 改写已有版本**被拒** | 断言库里那条一个字没变 |
| R3 | 版本链从新到旧列得出来 | 断言 `PlanVersions` 顺序 |
| R4 | 仓储**没有**改写类方法 | 反射断言（照 `RequirementRepo` 的做法） |

## S6.2 · 计划的产出

### ◐ U6.2.1 · 需求冻结后产出计划

| | |
|---|---|
| `goal` | 冻结需求 → 计划架构师产出 `plan v1` |
| `allowed_changes` | `backend/internal/app/work/**` · `backend/internal/api/**` · `api/openapi.yaml` |
| `forbidden_changes` | 未冻结的需求也能产计划（INV-REQ-1）；计划由需求分析师产出 |
| `stop_conditions` | 计划的结构化产出要靠解析 AI 的自由文本 —— 见下面的裁定 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 需求**没冻结**时拒绝产计划 | 断言报错且错误码可判定 |
| R2 | 产出时工作进入 `planning` | 断言状态迁移 + 事件 |
| R3 | 这一轮由**计划架构师**跑 | 断言 `AgentTurn.RoleID` 是它 |
| R4 | 重规划要给处置，缺一项就拒 | 断言 `ErrDispositionMissing` |
| R5 | 计划事件盖着 `plan_version` | 断言事件流里有它且带版本号 |
| R6 | AI 的回复能变成结构化的 `PlanVersion` | 断言一段带 JSON 的回复被解析出子计划与单元 |
| R7 | 解析不出来时**把原文给用户看**，不静默 | 断言事件里带着 AI 的原话与失败原因 |

**R1–R5 已完成。**

★★ **撞上了这个单元的停止条件，裁定如下**（2026-08-09）：

「计划的结构化产出要靠解析 AI 的自由文本」——这一条本来要停下来问，
但它**只有一个可行选项**，不构成需要用户裁决的取舍：

- ✗ 让用户手写计划：那正是 Duet 要替他做的事
- ✗ 让 AI 调一个我们定义的工具：ACP 的 `tool_call` 是 **Agent 侧**的工具，
  我们收得到通知但定义不了新工具
- ✓ **在 prompt 里要求它输出一段带标记的 JSON，后端从消息流里提取**

所以照第三条做，并把失败路径做实：

★ **解析不出来时把 AI 的原话原样给用户看**，附上失败原因。
静默失败的话，用户看到「正在规划」然后永远没有下文——
而真正的原因（AI 输出了一段散文）躺在一个没人读的地方。

## ★ 真机核对（2026-08-09）

逐条的实操记录跟在上面每条完成标志下面。**七条过六条**——
第 5 条（重规划的处置）要有一个已验收单元才谈得上，归 `M8`。

★★ 头一次真机跑时**抓到一个真 bug**：`cmd/duetd/wiring.go` 的 `eventStore` 是**逐字段
手抄**的翻译层（`eventbus.Event` ↔ `store.Event` 是两个具名类型，
depguard 不许基础设施互相 import，接缝只能落在 cmd）。给事件加
`role` / `requirement_version` 那五个字段时，domain、store、eventbus
三处都改了，**唯独这层没抄**——事件照样落库、照样读得回来，只是角色标签
没了，而所有单测都绿（它们不过这一层）。

**这是同一个失败模式的第六次**。这次的成因是结构性的：「逐字段手抄」
本身就是会漏的写法。所以补的测试不测字段值，测**「两个结构体字段数与
字段名逐个对上」**——下一个加字段的人当场看到红。

**核心假设验过了**：「AI 会照 `duet-plan` 围栏的格式输出 JSON」——
真 claude 一次就照做了，解析出 4 子计划 12 单元，十二个单元全派了角色。
