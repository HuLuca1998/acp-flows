## S5.1 · 常驻会话

### ✓ U5.1.1 · 会话池：按角色 + 工作维持长连接

| | |
|---|---|
| `goal` | 用户连说三句，AI 记得前两句 |
| `allowed_changes` | `backend/internal/acp/agent/**` · `backend/internal/app/work/**` |
| `forbidden_changes` | 每轮 `runtime.Start` + `session.Open`（那正是要改掉的）；把会话挂在 HTTP 请求的 ctx 上 |
| `stop_conditions` | 进程活着但会话已失效，且协议给不出判据 |

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 同一个工作连跑三轮，**只拉起一个进程** | 断言 Fake 收到的 `session/new` 次数为 1 |
| R2 | 第三轮的上下文里有前两轮 | 断言 Agent 那侧收到的 `sessionId` 三轮相同 |
| R3 | 工作 `paused` 时放掉进程，`executing` 时保持 | 断言两种状态下的进程数 |
| R4 | 会话断了要**显式降级**并告诉用户 | 断言事件流里有一条说明，而不是静默重开 |
| R5 | 一个工作的会话**绝不被另一个工作用到** | 造两个工作，断言 sessionId 不同 |
| R6 | 覆盖率 ≥ 85% | `make cover` |

**已完成**。★ 三条测试**先红发现了真问题**：

1. **`KillAgent` 只杀进程不摘会话**——下一轮会接到一条进程已死的会话上，
   表现是「prompt 石沉大海」，用户看着转圈而我们以为一切正常。
2. **开会话失败时丢了 Agent 的 stderr**——用户看到「对方已断开」，
   而真正的原因（「请先登录」）躺在一个没人读的管道里。
   开会话失败恰恰是最需要这条信息的时刻：那时还没有任何事件流。
3. **我把「先记进程再握手」的顺序改坏了**——原注释警告过：
   一个连 `initialize` 都不回的 Agent 会让 `session.Open` 挂住，
   而那时 `KillAgent` 找不到它。改成 `openSession` 收一个
   `onProcess` 回调，进程一起来就交出去。

★ `LeavesNoOrphan` 的判据跟着设计改了：从「跑完进程必须死」
改成「三轮只起一个进程 + 跑完还活着 + ReleaseWork 之后收干净」——
**比原来更强**，它同时守住「复用」与「不泄漏」。

### ◐ U5.1.5 · 上一轮还在跑时，这一句要排队

| | |
|---|---|
| `goal` | 上一轮没跑完就再说一句，那一句**排在后面**而不是被吃掉 |
| `allowed_changes` | `backend/internal/acp/agent/**` · `backend/internal/app/work/**` · `frontend/src/features/chat/**` |
| `forbidden_changes` | 直接拒绝第二句（用户会以为应用坏了）；把队列挂在 HTTP 请求的 ctx 上 |
| `stop_conditions` | 协议给不出「这一轮结束了」的可靠判据 |

**为什么有这个单元**（2026-08-09 真机发现）：`Say` 直接 `runTurn`，
上一轮还在跑时两个 prompt 会同时打到同一条会话上。库里能看到连着两条
`turn_end`，而**第二句的回答一个字都没有**——用户补充一句之后没有任何
回应，而界面看起来一切正常。

ACP 的一条会话一次只跑一轮，这不是可以并发的东西。

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 上一轮在跑时，第二句**排队**不下发 | 断言 Fake 收到的 `session/prompt` 是串行的（前一条回完才有下一条） |
| R2 | 排着的那句**不丢** | 断言前一轮结束后它被发出去，且文本一字不差 |
| R3 | 界面上说清「它还在忙，你这句排在后面」 | 断言排队时有可见提示，而不是静默 |
| R4 | 取消整个工作时，排队里的**一并丢弃** | 断言取消后队列清空，且不再下发 |
| R5 | 排队深度有上限，超了明确拒绝 | 断言第 N+1 句被拒且说明原因 |

**R1 R2 R4 R5 已完成**（`acp/agent/gate.go`）。R3（界面上说清「它还在忙」）
欠着——要等对话页有排队态可显示。

★★ 两处值得单独说：

1. **用带 ctx 的 channel 而不是 `sync.Mutex`**。mutex 等不了 ctx——
   用户点了停，排在后面的那几轮会**照样一句句跑完**。
2. **排队满不推 `failed`**。哨兵错误定义在 `port`（app 不许 import acp），
   app 层据此把它与「AI 跑挂了」分开：推到 failed 的话，用户只是手快点了
   几下就得重开一个工作，而他那几句话其实一句都没丢，只是没排上。

★ `release` 用 `sync.Once` 包着：调两次会取走下一轮刚放进去的令牌，
那一轮永远等不到自己结束——整条会话从此卡死，而表现是「界面一直转圈」。
写测试时自己踩了一次（`defer first()` 加显式 `first()`），当场挂死 60 秒超时。

### ◐ U5.3.2 · 消息带头像与左侧色条

| | |
|---|---|
| `goal` | 一屏扫过去，**不读文字**就分得清哪几条是同一个人说的 |
| `allowed_changes` | `frontend/src/features/timeline/**` |
| `forbidden_changes` | 头像用图片（要联网）；按角色 id 硬编码颜色（角色会增删） |
| `stop_conditions` | 设计稿的头像缩写规则与 Runtime 名对不上 |

**为什么补这个单元**（2026-08-10 对照设计稿发现）：`U5.3.1` 做了角色**标签**，
而设计稿的角色分栏主体是**头像方块 + 左侧色条**（`CL` 紫、`CX` 灰）。
只有标签的话，用户一屏扫过去要**逐条读文字**才分得清说话的人——
而头像是更快的那条路，也是设计稿真正在做的事。

**验收标准**

| # | 标准 | 断言 |
|---|---|---|
| R1 | 有角色的消息带头像方块 | 断言头像存在且带 runtime 缩写 |
| R2 | 缩写由 **Runtime 名**推导，不硬编码 | 断言 `claude`→`CL`、`codex`→`CX`、没见过的也有两个字母 |
| R3 | 不同 Runtime 的头像**看得出不同** | 断言 `data-runtime` 不同 |
| R4 | 没有角色的事件**不画头像** | 断言 state_change 这类没有 |
| R5 | 用户自己说的话也不画 | 断言右对齐气泡里没有头像 |

**R1–R5 全部完成。**

★★ R2 的前提是先有 `user_message` 事件——**在此之前用户自己说的话
根本不在时间线上**，对话页只有 AI 的独白。而「它有没有听懂我」正是靠
两句话对照看出来的。

★★ R3 顺带改了合并规则：**需求版本不同就不并进同一个气泡**——
并进去的话标签只剩一个，用户看不出「哪句话之后需求变成了 v2」。

★ 角色**由后端盖在每条事件上**（`role` / `role_display_name` / `runtime`），
前端不许按 Runtime 名猜：一个 Runtime 可以承担多个角色
（`claude` 同时是需求分析师和审查员），按名字猜的话
界面上两个角色会长得一模一样。

★★ 合并规则也跟着改了：**角色不同就不并进同一个气泡**——
那是两个人在说话，并进去的话标签只剩一个，用户分不清哪句是谁说的。
