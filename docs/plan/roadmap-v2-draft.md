## 为什么要重排

旧排法是**按技术切**（传输层 → 会话 → 事件流 → 权限 → 取消 → 检查点），
做出来每一块单测都绿，但**用户拿不到一件完整的事**：

- 对话页做完了，而它上面的六层（项目 / 工作 / 需求 / 计划 / 契约 / 角色）全是空的
- 结果是一个「聊天框」——没有角色、没有注入、没有契约边界

新排法**按引用关系的拓扑序**，每个里程碑是**用户能独立做成的一件事**。

## ★★ 一条硬约束：对话会话必须长期存活且只读

**2026-08-08 用户裁定**（见 [`open-questions.md`](open-questions.md) Q42）：

> 「一个对话里面，和用户沟通的 AI 只能是**同一个会话**，只有**读取权限**，
> 用于修改创建计划，不要每次用户发送消息、补充消息就启动一个新的会话。」

**我现在做错了**：`ProcessRunner.RunTurn` 每一轮都拉一个新进程、开一条新会话、
跑完就杀掉。后果——

- 用户「补充一句」时，AI **不记得上一句**（上下文每轮清零）
- 每轮重付一次启动与上下文成本
- 「一次对话」在协议上是一条会话，我做成了 N 条互不相干的

**正确的形态**：

| 谁 | 会话 | 权限 |
|---|---|---|
| 与用户沟通的（需求分析师 / 计划架构师 / 单元设计师） | **一条常驻会话**，跨轮复用 | **只读**——只产出需求、计划、契约，不碰文件 |
| 实现工程师 | 每个单元一条独立会话 | 按契约写入边界，动文件走权限请求 |
| 实现审查员 | **独立会话**（设计稿角色卡原文：「不延续规划会话」） | 只读 |

★ 「只读」怎么落实：设计稿角色表里有一列 **`会话模式 set_mode`**（值 `plan`）——
**用 ACP 的 `set_mode` 收权**，而不是靠我们自己拒绝每个请求。

这条改变了 `M4` 与 `M6` 的验收标准，见下。

## ★★ 三条用户裁定（2026-08-08）

### 裁定一：记忆 / Skill / 角色**先做**

> 「你需要先完成记忆、skill、agent。」

我原草案把它们排在 `M9` / `M10`（「越用越懂你」「我能调教它」），**排错了**。
它们不是锦上添花，是**基础设施**：

- 创建项目时要**扫描已有 skills**、初始化 `memory/` —— 得先有库的结构
- 对话 AI 要**读取**记忆与 skill —— 得先有东西可读
- 计划里每个单元要**分配角色** —— 得先有角色

所以提到 `M2`，排在「创建项目」之前。

★ 有个先后要理清：Skill 与记忆各有**两层**（项目级 `<项目>/.acpflows/`
与全局级 `~/.acpflows/`）。**先做全局级**——项目级的在创建项目时初始化，
那时才有项目。

### 裁定二：对话 AI **能读**记忆、Skill、代码，只是不能写

> 「软件里面和用户对话的 ai 需要能使用、读取。」

这是对 Q42「只读」的具体化。**只读 ≠ 什么都不能做**：

| 能 | 不能 |
|---|---|
| 读项目代码（理解现状才能提计划） | 写/删任何文件 |
| 读记忆库（知道这个项目的规矩） | — |
| 读 Skill 库（知道有哪些可用的做法） | — |
| 产出需求、计划、契约（写进 Duet 自己的库） | 动用户的工作区 |

★ **在 ACP 层收权**（2026-08-08 用户确认），不是我们自己拦每个请求。
实测数据摆在那儿（`acp-field-notes.md` §3）：

| 做法 | 权限请求次数 | 文件建了吗 |
|---|---|---|
| codex 默认档 + **我们全拒** | **0** | ✅ **建了** |
| `read-only` 档 + 我们全拒 | 2 | ❌ 没建 |

**一份看起来很严的全拒代码，在默认档下从未被调用过**——
`agent` 档是 `workspace-write` 沙箱，沙箱内的写操作根本不触发审批。

★★ 用 **`session/set_config_option`**，不是 `set_mode`——后者官方已废弃
（`acp-field-notes.md` §7 裁定 3）。先试新的，不支持再降级，
**两个都不支持就明确报错拒绝开工**，不假装收了权。

### 裁定三：计划里**每个单元都要分配角色**

> 「他写出来的计划，每一条都需要他分配好使用哪个角色去工作。」

计划架构师产出计划时，**每个单元要指定由哪个角色执行**——
不是到执行时才决定，也不是固定「都归实现工程师」。

模型上：`Unit` 要有 `role` 字段，且**必须**是角色库里存在的一个。
界面上：计划面板每个单元条目显示它的角色。

★ 设计稿依据：对话里 `Codex · 实现工程师` 与 `unit-012` 是绑在一起显示的；
角色表有一列「角色 / **承担的 AI 操作**」。

## 每个里程碑的完成标志（用户自己做的几步）

### M2 · 它有了角色、技能和记性

★ 这一步用户**看得到但还用不上**——它是后面所有事的地基。
完成标志按「看得到、改得动」验，不按「跑通一轮对话」验。

1. 打开「角色与 Runtime」页 → 看到**五个内置角色**的表：
   需求分析师 / 计划架构师 / 单元设计师 / 实现工程师 / 实现审查员，
   每行有「承担的操作」「性格与语气」「Runtime」「会话模式 set_mode」「权限裁决」
2. 打开「Skill」页 → 看到**全局 Skill 库**（`~/.acpflows`），
   每条带**版本号**、状态（active / draft）、**校验没过时说明原因**
3. 打开「记忆」页 → 看到**跨项目记忆**（`~/.acpflows`），
   每条带**类型**（constraint / experience）与状态（active / 候选 / 已失效）
4. 三个库都能筛选（Skill 按项目/全局，记忆按状态）
5. ★ 三个页面**不再是骨架占位**

6. ★★ 角色的「会话模式」列能选档位，取值是**实测的那三个**
   （`read-only` / `agent` / `agent-full-access`）——
   **不是设计稿写的 `auto`**（那是 codex 0.16.0 的旧档名，1.1.7 已改）
7. ★★ 选了 `read-only` 的角色，开会话时真的发出 `session/set_config_option`；
   Runtime 不支持时**降级到 `set_mode`**；两个都不支持 → **报错拒绝开工**

**验收依据**：`INVENTORY.md` §八（角色表）§九（记忆页）§十（Skill 页）+ **Q42**
**★ 顺带迁移**：把 `session.Policy`（三种权限策略）从会话层挪到角色层
**★ 补上三层防线的第 ①层**：现在只有 ②隔离 cwd，缺 ①Runtime 沙箱档

### M3 · 把我的项目交给它

1. 点左栏「＋ 创建项目」→ **弹出对话框**，选一个本地文件夹
2. 对话框里看到「将创建 `<项目>/.acpflows/`（skills/ · memory/ · project.yaml）」
3. 对话框里看到「将追加 `.gitignore` — 忽略 `.acpflows/runs/`」
4. 对话框里看到「**发现已有 Skill 目录 · N**」，列出扫到的 `.claude/skills/` 等，
   标出哪些**校验没过**（如「缺 description」）
5. 看到 GitHub remote 与对应账号（有 remote 时）
6. 点「创建项目」→ 项目出现在左栏，**磁盘上真的多了 `.acpflows/`**
7. 提示明确：「创建项目不会开始任何工作」

**验收依据**：`INVENTORY.md` §五（弹层 1）+ §二（左栏项目区）

### M4 · 开一个工作

1. 点项目下的「＋ 新建对话」→ **弹出「新建工作」对话框**
2. 看到「已检测到 `.git` · 无未提交改动」（或如实报告有改动）
3. 选基线分支：`main` / `develop` / 「指定 commit…」
4. 看到将创建的分支名与 worktree 路径、基线 commit
5. 点「创建 worktree 并开始」→ 工作出现在项目下，**磁盘上真的多了 worktree**
6. 右栏出现「工作区」：分支、领先几个 commit、未提交改动、本次工作的 commit
7. 创建失败时工作进入 `initializing_failed`，**不退回原目录执行**

**验收依据**：`INVENTORY.md` §六（弹层 2）+ §四（右栏工作区）

### M5 · 说一句需求，它追问清楚并冻结

1. 输入一句需求 → **`Claude · 需求分析师`** 追问细节（不是直接开写）
2. 每条消息带**角色标签**与身份（头像 + 名字 + 角色）
3. 追问清楚后产出 `requirement v1`，标「**已冻结**」
4. 需求改一次 → 版本变 `v2`，旧版留着
5. 设置里看得到角色的默认绑定（需求分析师=claude 等），**这一步还不能改**
6. ★★ **连着说三句话，AI 记得前两句**——不是每句都从零开始（一条常驻会话）
7. ★★ 这条会话**只读**：让它「改一下 README」，它**做不到**——
   ★ 判据是**磁盘上没有那个改动**，而不是「界面上弹了权限卡片被我拒了」。
   收权在 Runtime 那一侧（`set_config_option`），我们这侧根本收不到请求
8. ★★ **它读得到东西**（裁定二）：问它「这个项目有什么规矩」，
   它能引用记忆库里的条目；问它「有哪些可用的 Skill」，它答得出来；
   问它代码里某个函数干嘛的，它读得到

**验收依据**：`INVENTORY.md` §三.2（消息流角色）+ §八（角色表）+ **Q42 + 裁定二**

### M6 · 它给出计划，每条都派好了人

1. 需求冻结后 → **`Claude · 计划架构师`** 产出 `plan v1`，标「N 子计划 · M 单元」
2. 打开计划面板 → 看到**子计划 DAG**：每个子计划的状态与进度（`accepted · 3/3`）
3. 每个子计划下挂**单元**，带状态与依赖（`依赖 unit-012 · 契约未冻结`）
4. 看到**变更历史**：计划改过几版、每次为什么改
5. 重规划时**必须声明**已验收工作的处置（仍有效 / 需补充 / 需回滚 / 已废弃）
6. ★★ **每个单元都标着由哪个角色做**（裁定三）——
   计划面板上每条单元显示 `实现工程师` / `单元设计师` 等
7. ★★ 分配的角色**必须是角色库里存在的**：计划里写一个不存在的角色 → 报错，
   而不是到执行时才发现没人认领

**验收依据**：`INVENTORY.md` §三.1（右上角浮标）+ 计划面板各项 + **裁定三**
**已有**：`U4.2.1` 的 `PlanVersion` 与 `Disposition`（后端模型 + 反射不可变检查）
**要加**：`Unit.role` 字段 + 「角色必须存在」的校验

### M7 · 它按契约干活，我看得见管得住

1. 单元开始前 → **`Claude · 单元设计师`** 产出契约 `v1`，可查看全文（YAML）
2. 契约冻结后不能改；要改就出 `v2`，旧版留着
3. 干活时每条消息显示**注入了什么**：`skill:xxx@版本 · mem-xxx`
4. AI 要动文件 → 权限卡片，**标出是否在写入边界内**（边界来自契约）
5. 点「停」→ AI 真的停，现场保留
6. 本轮结束显示「本轮小结」四行（计划变更 / 契约 / 注入清单 / 处理方式）
7. ★★ **实现工程师是另一条会话**——它写文件，而与你对话的那条始终只读
8. ★★ 一个单元跑好几轮时，实现会话**也是同一条**（记得自己刚改过什么）

**验收依据**：`INVENTORY.md` §三.2（消息流全部）+ §七（契约弹层）+ **Q42**
**已有**：对话流、权限卡片、两段式取消（`M2`/`M3` 旧编号做的）

### M8 · 它说做完了，我能验

1. 单元跑完 → 看到「验收证据 N 条 / 标准 M 条」

3. 每条验收标准旁边标 `✓ ev-441` 或 `○ 无证据`
4. 证据是**应用直接采集的**，不是 AI 转述的
5. 验收通过 → 自动提交到工作分支 + 落检查点（`ck-07 · abc123`）

**验收依据**：`INVENTORY.md` §七（证据四类）+ §四（commit 列表）
**已有**：检查点与恢复（`U4.1.2`）
