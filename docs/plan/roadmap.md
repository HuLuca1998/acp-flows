## 为什么 2026-08-08 重排

用户打开应用后说了三句话，每一句都指向同一个问题：

> 「为什么菜单没有显示项目列表和对话记录」
> 「我辛辛苦苦设计原始稿，就是想让你跟着原始稿工作，结果你做出来的就是一坨屎」
> 「特别是对话页面你只做了设计稿的 1%」

**根因不是没读设计稿，是读它的方式是 grep。** grep 只能找到已经知道要找的东西——
不知道左栏该有项目列表，就不会去 grep 它。这是检索方式的结构性盲区。

于是先把设计稿**整个**拆了一遍，再按引用关系重排：

| 产物 | 内容 |
|---|---|
| [`design/INVENTORY.md`](../../design/INVENTORY.md) | 逐屏渲染 + DOM 遍历拆出的 **52 项**功能点，当时做了 11 项 |
| [`design/DEPENDENCIES.md`](../../design/DEPENDENCIES.md) | 18 条引用关系 + **L0–L11 拓扑序** |
| [`design/PARITY.md`](../../design/PARITY.md) | 46 区块逐个表态（一致/增强/简化/待实现/偏离），有机器检查守着 |

`DEPENDENCIES.md` 的结论一句话：**我实际的做法是 L7 → L2 → L1，正好倒过来。**
对话页（L7）做完了，而它上面六层（项目 / 工作 / 需求 / 计划 / 契约 / 角色）全是空的，
结果是一个「聊天框」。

## ★★ 三条用户裁定（2026-08-08，必须遵守）

### 裁定一：记忆 / Skill / 角色**先做**

> 「你需要先完成记忆、skill、agent。」

它们不是锦上添花，是基础设施。原草案排在 `M9`/`M10`，**排错了**，已提到 `M2`。

★ 先做**全局级**（`~/.acpflows`）：项目级的在创建项目时初始化，那时才有项目。
反过来的话 `M2` 就得依赖 `M3`，环绕回去了。

### 裁定二：对话 AI **能读**，只是不能写

> 「软件里面和用户对话的 ai 需要能使用、读取。」

| 能 | 不能 |
|---|---|
| 读项目代码（理解现状才能提计划） | 写 / 删任何文件 |
| 读记忆库（知道这个项目的规矩） | — |
| 读 Skill 库（知道有哪些可用的做法） | — |
| 产出需求、计划、契约（写进 Duet 自己的库） | 动用户的工作区 |

★ **在 ACP 层收权**，不是我们自己拦每个请求。实测数据（`acp-field-notes.md` §3）：

| 做法 | 权限请求次数 | 文件建了吗 |
|---|---|---|
| codex 默认档 + 我们全拒 | **0** | ✅ **建了** |
| `read-only` 档 + 我们全拒 | 2 | ❌ 没建 |

**一份看起来很严的全拒代码，在默认档下从未被调用过**——
`agent` 档是 `workspace-write` 沙箱，沙箱内的写操作根本不触发审批。

★★ 用 **`session/set_config_option`**，不是 `set_mode`（后者官方已废弃）。
先试新的，不支持再降级，**两个都不支持就明确报错拒绝开工**，不假装收了权。

### 裁定三：计划里**每个单元都要分配角色**

> 「他写出来的计划，每一条都需要他分配好使用哪个角色去工作。」

模型上：`Unit` 要有 `role` 字段，且**必须**是角色库里存在的一个。
界面上：计划面板每个单元条目显示它的角色。

## ★★ 一条硬约束：对话会话必须长期存活且只读

**Q42 裁定**（[`open-questions.md`](open-questions.md)）：

> 「一个对话里面，和用户沟通的 AI 只能是**同一个会话**，只有**读取权限**，
> 用于修改创建计划，不要每次用户发送消息、补充消息就启动一个新的会话。」

**现在做错了**：`ProcessRunner.RunTurn` 每轮拉一个新进程、开一条新会话、跑完杀掉。
后果是用户「补充一句」时 AI 不记得上一句。

| 谁 | 会话 | 权限 |
|---|---|---|
| 与用户沟通的（需求分析师 / 计划架构师 / 单元设计师） | **一条常驻会话**，跨轮复用 | **只读** |
| 实现工程师 | 每个单元一条独立会话 | 按契约写入边界，动文件走权限请求 |
| 实现审查员 | **独立会话**（设计稿原文：「不延续规划会话」） | 只读 |

这条改变了 `M5` 与 `M7` 的验收标准。

## M5–M12 的验收条件

到 `M5` 时把这一节对应的部分抽成 `milestones/M5-*.md`，并拆出单元。
**验收条件现在就定死**，拆单元时不许放宽。

### M5 · 说一句需求，它追问清楚并冻结

1. 输入一句需求 → **`Claude · 需求分析师`** 追问细节（不是直接开写）
2. 每条消息带**角色标签**与身份（头像 + 名字 + 角色）
3. 追问清楚后产出 `requirement v1`，标「**已冻结**」
4. 需求改一次 → 版本变 `v2`，旧版留着
5. ★★ **连着说三句话，AI 记得前两句**——不是每句都从零开始（一条常驻会话）
6. ★★ 这条会话**只读**：让它「改一下 README」，它**做不到**。
   ★ 判据是**磁盘上没有那个改动**，而不是「界面上弹了权限卡片被我拒了」——
   收权在 Runtime 那一侧，我们这侧根本收不到请求
7. ★★ **它读得到东西**（裁定二）：问它「这个项目有什么规矩」，它能引用记忆库条目；
   问它「有哪些可用的 Skill」，它答得出来；问它某个函数干嘛的，它读得到

**依据**：`INVENTORY.md` §三.2 + §八 + **Q42 + 裁定二**

### M6 · 它给出计划，每条都派好了人

1. 需求冻结后 → **`Claude · 计划架构师`** 产出 `plan v1`，标「N 子计划 · M 单元」
2. 计划面板看到**子计划 DAG**：每个子计划的状态与进度（`accepted · 3/3`）
3. 每个子计划下挂**单元**，带状态与依赖（`依赖 unit-012 · 契约未冻结`）
4. 看到**变更历史**：改过几版、每次为什么改
5. 重规划时**必须声明**已验收工作的处置（仍有效 / 需补充 / 需回滚 / 已废弃）
6. ★★ **每个单元都标着由哪个角色做**（裁定三）
7. ★★ 分配的角色**必须是角色库里存在的**：写一个不存在的角色 → 报错，
   而不是到执行时才发现没人认领

**已有**：`PlanVersion` 与 `Disposition`（后端模型 + 反射不可变检查）
**要加**：`Unit.role` 字段 + 「角色必须存在」的校验

### M7 · 它按契约干活，我看得见管得住

1. 单元开始前 → **`Claude · 单元设计师`** 产出契约 `v1`，可查看全文（YAML）
2. 契约冻结后不能改；要改就出 `v2`，旧版留着
3. 干活时每条消息显示**注入了什么**：`skill:xxx@版本 · mem-xxx`
4. AI 要动文件 → 权限卡片，**标出是否在写入边界内**（边界来自契约）
5. 点「停」→ AI 真的停，现场保留
6. 本轮结束显示「本轮小结」四行（计划变更 / 契约 / 注入清单 / 处理方式）
7. ★★ **实现工程师是另一条会话**——它写文件，而与你对话的那条始终只读
8. ★★ 一个单元跑好几轮时，实现会话**也是同一条**（记得自己刚改过什么）

**已有**：对话流、权限卡片、两段式取消

### M8 · 它说做完了，我能验

1. 单元跑完 → 看到「验收证据 N 条 / 标准 M 条」
2. 点开证据 → **四类**：Git diff · 测试输出 · 命令记录 · 审查意见
3. 每条验收标准旁边标 `✓ ev-441` 或 `○ 无证据`
4. 证据是**应用直接采集的**，不是 AI 转述的
5. 验收通过 → 自动提交到工作分支 + 落检查点（`ck-07 · abc123`）

**已有**：检查点与恢复

### M9 · 拿不准的它来问我

1. 遇到高等级决定 → 工作进入 `waiting_user`，左栏那条**亮蓝点**
2. 点开 → D2 弹层：契约全文 + 版本切换 + 验收标准与证据
3. 看到**三个选项**，每个带影响分析，其中一个标「**推荐**」
4. 选一个 → 写入 `Decision` 记录 + 生成新的契约或计划版本
5. 「稍后决定」不丢现场

### M10 · 它越用越懂我的项目

1. 干活中冒出经验 → 消息里出现「**记忆候选**：… · 审核」
2. 点「审核」→ 决定收不收；收了进记忆库
3. 记忆页：按项目 / 跨项目分组，按 `active / 候选 / 已失效` 筛选，有类型
4. Skill 页：带**版本号**、**命中计数**、**校验态**（draft 说明为什么没过）
5. 下一轮对话的注入行里，能看到刚收的那条记忆

### M11 · 我能调教它

1. 角色页：八个角色各自的 Runtime、会话模式、**权限裁决**、提示词
2. 改一个角色的 Runtime（claude ↔ codex）→ 下一轮真的换了
3. 改「权限裁决」（**逐条询问 / 自动允许读**——设计稿只有这两个取值，
   没有「一律拒绝」）→ **只影响这个角色**
4. 编辑角色提示词 → 下一轮生效

★ `session.Policy` 从会话层迁到角色层的活在 `M2` 就做（定义角色时一起做），
不等到这里——放错层的东西留着会让 `M7` 的权限卡片也跟着错。

### M12 · 我看得到它干得好不好

1. 报表页：单元一次通过率 · 平均单元耗时 · 每日已验收单元 · Runtime 使用
2. 可切「近 30 天 / 全部项目」
3. 审查驳回原因分布

```
① 里程碑 → ② 拆分单元 → ③ 单元实现计划
        → ④ 单元测试（代码）→ ⑤ 操作测试（UI）→ ⑥ 通知用户测试
```

## 怎么用这份文档

- **接到一个需求先问它属于哪个里程碑。** 对不上任何一条 → 用 `create-issue` 记下来，别顺手做
- 里程碑内的编号（`U3.1.2`）可直接用作 issue 标签与分支 slug
- **一个单元六步走完就在里程碑里标 `✓` 并注明提交号**
- `✓` 的含义是**六步全走完**，不是「代码写完了」
- ★ 里程碑标「完成」前，**每条完成标志都要留一行 `> 实操：<在哪验的，看到了什么>`**——
  「单元测试全绿」不算：单元是我的切法，完成标志是用户的切法，两者不重合
