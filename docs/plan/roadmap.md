## 排期原则

1. **地基先行** —— 没有 Fake ACP Runtime，上层一切都测不了
2. **发布链路早通** —— 用户指定优先。越早跑通，后面每次交付成本越低
3. **垂直切片，不横向铺** —— 先打穿一条主链路，而不是把 7 个页面都铺成静态页

## M1 · 发布与自动更新（用户指定优先）

**目标：合并一个 PR 就能发出一个用户装得上、且能自动更新的版本。**

**可与 M0 并行**（不同 worktree）—— 它几乎不碰领域逻辑，交集只有 `/v1/system/*` 几个端点。

| # | 交付物 | 验收 |
|---|---|---|
| 1.1 | CI 四个 job | `docs` `contract` `backend` `frontend` 全绿，且能真的拦住违规 |
| 1.2 | `main` 分支保护 | 直接 push 被拒；PR 必须过 CI；仅 squash；线性历史 |
| 1.3 | 手动触发发版（**不用 release-please**） | `gh workflow run release -f version=X.Y.Z`；版本号发布时 jq 注入，仓库里始终 0.0.0。见 `adr/0007` |
| 1.4 | Tauri 壳最小可用 | 无边框窗口 + 42px 自绘窗口栏 + sidecar 拉起 `duetd` |
| 1.5 | 构建与 **minisign 签名** | tag 触发，产出 universal `.app`/`.dmg` + `.sig` + `latest.json`，发布到 GitHub Release |
| 1.6 | 客户端检测更新 | **进设置页时检查，不轮询**；显示当前版本/新版本/更新说明/体积。见 `adr/0007` |
| 1.7 | **`POST /v1/system/update/prepare`** | 无进行中工作时直接放行；有工作时暂停 + 落检查点；Runtime 无响应时返回 `blocked` 且**不落检查点** |
| 1.8 | 一键更新并重启 + 恢复 | `prepare` → 下载 → 装 → 重启 → `GET /v1/system/resume` 列出可恢复工作 |
| 1.9 | Runtime 更新（第二条线） | 从 npm 装 `claude-agent-acp` / `codex-acp` 到多版本目录，探针全过才允许切换 |

> 1.7 的完整语义依赖 M0 的 `Work` 状态机与 checkpoint。
> **实现顺序**：先做「无工作时直接放行」的版本，M0 的 0.7 到位后再补全暂停与落检查点。
> 这样 1.1–1.6 可以立刻开始，不必干等。

**M1 的完成标志**：能给别人发一个链接，对方装上，下次发版他能收到更新提示并一键更新成功。

## M2 · 主链路垂直切片

**目标：一条端到端能跑通的真实工作流。**

```
创建项目 → 新建工作(切 worktree) → 需求澄清 → 计划冻结
→ 单元契约冻结 → Codex 执行 → 权限裁决 → 证据采集
→ 独立审查 → 验收 → 自动提交 → 检查点落盘
```

| # | 交付物 |
|---|---|
| 2.1 | 项目管理：添加本地仓库、初始化 `.acpflows/`、导入已有 skills |
| 2.2 | worktree 生命周期：创建、失败进 `initializing_failed`、清理 |
| 2.3 | 8 个角色与 Runtime 绑定、`set_mode`、权限裁决策略 |
| 2.4 | 计划 / 子计划 DAG / 单元契约的完整状态机与持久化 |
| 2.5 | 对话页 + **13 类事件渲染器**（注册表模式）+ 过滤器 |
| 2.6 | 悬浮计划面板、契约抽屉、证据抽屉 |
| 2.7 | 决策 D1–D3：等级判定、`waiting_user` 阻塞、选项与推荐 |
| 2.8 | 证据采集（**应用直接采集，非 Agent 转述**）+ 检查点 + 自动提交 |
| 2.9 | E2E 黄金路径一直绿 |

## 怎么用这份文档

- **接到一个需求先查它属于哪个 M。** 不属于当前 M 的 → 用 `create-issue` skill 记下来，别顺手做了
- 里程碑内的编号（`1.7`）可直接用作 issue 标签与分支 slug
- **完成一项就在这里划掉并注明 PR 号**，让下一轮 AI 知道进度
