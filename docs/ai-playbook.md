# AI 工作手册：走哪条路、读哪份文档

> **这份文档解决两件事**：
> ① 你现在处于什么情形 → 该走哪条路
> ② 上下文有限 → 该读什么、不该读什么
>
> 本文自己也遵守规则：**整篇 < 2500 token，可以整篇读。**

---

## 1. 上下文预算：为什么不能全读

| 层 | 内容 | 体量 |
|---|---|---|
| **L0 常驻** | 根 `AGENTS.md` + `CLAUDE.md` | ~6k tok |
| **L1 阶段加载** | 1 个 skill + 1 份目录 `AGENTS.md` | ~1.5k tok |
| **L2 按需检索** | 34 份专题文档 | **~183k tok** |

**全部加起来 216k，超过 200k 上下文窗口。** 一次全读物理上做不到，
就算做到也没有余量干活了。

所以规则是硬的：

| 层 | 怎么读 |
|---|---|
| L0 | 自动在上下文里，**不用主动读** |
| L1 | 开工时读**一个** skill + **一份**就近的目录 `AGENTS.md` |
| L2 | **永远 grep 定位到章节，绝不整篇读** |

### L2 的正确读法

```bash
# ✗ 一次吃掉 27k token，占 13% 上下文
Read docs/acp-integration.md

# ✓ 先定位，再只读那一段
grep -n "两段式取消" docs/spec/acp-integration.md     # → 行号
Read docs/acp-integration.md offset=420 limit=80
```

**超过 8k token 的文档顶部都有「读法」块**，写明章节索引与定位方式。
看到那个块就说明：不要整篇读。

## 3. 一个任务的标准路径

```
① 定位     读 tdd-unit skill + 目标目录 AGENTS.md
              └ 需要细节时才 grep 专题文档的对应章节
② 边界     写下：允许改什么 / 禁止改什么 / 什么情况停下来
③ 写失败测试  跑一次，确认是红的 ★ 这步不能跳
④ 最小实现  只写到测试变绿
⑤ 验证     make check  +  make dev 起服务实测（用完 make dev-stop）
⑥ 自查     债务体检 · 抽取检查 · 索引登记
⑦ 提交     Conventional Commits，写明「先红的测试」
⑧ 合并后   make tidy
```

细节在 `tdd-unit` skill 里，**不要为了看这 8 步去读它**——这里就是全部。

## 4. 卡住了怎么办

按这个顺序，**不要跳过前面直接猜**：

1. **拿着报错原文 grep 踩坑档案** —— 最便宜、命中率最高的一步：
   ```bash
   grep -n "你看到的报错原文" docs/notes/pitfalls.md
   ```
   这些坑本项目都真实踩过并花了时间解决。命中一条能省几十分钟。
2. **查 `plan/open-questions.md`** —— 这个问题是不是已经有裁定了？
   （整篇 ~2k，可以全读）
3. **查 `adr/`** —— 是不是有 ADR 解释了为什么这么定？`ls docs/adr/` 看标题就够
4. **查前一个项目** —— `~/work/ai-workflows` 是同一作者的前作，形态相同。
   **它是 A 级证据**，「以前做过」的事优先看它，别从零推导
5. **能不能用实测代替推理？** —— `make probe`（ACP 行为）、写个探针、跑一次看看
6. **还是不确定 → 停下来问人。** 把问题加进 `plan/open-questions.md` 的「仍需拍板」

**解决之后**：如果这个坑花了 >15 分钟且会再次发生，按
[`notes/pitfalls.md`](notes/pitfalls.md) 的维护规则加一条——
**但先问能不能变成检查**，能变成检查的不要写进文档。

**不许做的**：猜一个做法然后当成事实往下写。猜错的代价由后面所有轮次承担。

## 4.5 从零开工：按里程碑顺序做什么

**M0 → M1 → (M2) → (M3 ‖ M4)。** 每个里程碑内部的并行链见各章的「子计划 DAG」。

| 顺序 | 里程碑 | 第一个该做的单元 | 前置 |
|---|---|---|---|
| 1 | **M0** 地基 | **`U0.4.2` Fake 的权限请求与能力矩阵** ★ | `U0.2.3`、`U0.4.1` 已完成 |
| 2 | M1 发布与更新 | `U1.1.1` 工程门禁 → `U1.3.1` Tauri 壳 | M0 的 `S0.6`（`prepare` 依赖两段式取消） |
| 3 | M2 主链路 | `U2.1.1` 契约冻结 ◆ | M0 全部 |
| 4a | M3 记忆与 Skill | `U3.1.1` 记忆 md 读写 | M2 |
| 4b | M4 产品面 | `U4.3.1` 凭据保管 | M2（与 M3 可并行，不同 worktree） |

**M0 里可立即并行开的三条**（互不重叠）：

```
U0.4.2      Fake 的权限请求与能力矩阵  ← 关键路径（挡着 S0.6 两段式取消），优先派人
U0.2.2      子进程生命周期             ← 与 Fake 无交集
U0.9.2      PlanVersion/契约冻结       ← 纯 domain，与协议层零交集
```

> **`U0.2.3` 是 2026-08-07 补登记的**（现已完成）。原先这里写「`U0.4.1` 可立即开工」
> 是错的：`fake` 只允许 import `protocol`，而那个包当时并不存在。
> **开工前先 `ls` 一眼你要 import 的包在不在**——里程碑说"可立即开工"不代表前置真的就绪。

**开工前只需读三样**：`tdd-unit` skill · 目标目录的 `AGENTS.md` · 你那个单元那一节。
里程碑章的「读法」块告诉你怎么只读那一节。

**唯一还需要人拍板的是 Q5**（Apple 开发者证书 $99/年），**它不挡任何事** ——
M1 在 ad-hoc 签名下能完整跑通。

## 4.6 自主循环 ★ 「继续按里程碑工作」是什么意思

用户说这一句时，他授权的是**一个不需要他参与的循环**：

```
① 读 roadmap.md 找到「下一个该做的单元」
② 走六步流程做完它（milestones/README.md）
③ commit —— 一个逻辑单元一个，不要攒
④ 攒够一批（一个子计划或一个完整主题）→ 开 PR → 等 CI 绿 → 自己合并 → make tidy
⑤ 完成一个里程碑 → **通知用户可以验收什么**
⑥ 不等他回复，回到 ①
```

**第 ⑤ 步只是通知，不是提问。** 用户明确要求过：告知即可，不必等测试报告。
他有意见会主动说；没说就继续做下一个单元。

**第 ④ 步的 PR 与合并由你自己决定时机**（`gh-pr` / `gh-pass` skill）。
判断标准是「这一批合起来是不是一个能独立审查的主题」，不是「攒了几个 commit」。

### 什么时候必须停下来找人

只有三类。除此之外一律自己决断并在回复里说明理由：

| 情形 | 例子 |
|---|---|
| **凭据类操作** | `gh secret set` 私钥/令牌。**用户授权也不解除**——见 `M1` 的 `U1.2.1` |
| 铁律里写明「立刻停」的 | 撞上 `open-questions.md` 未决项、需要越界改动、发现架构假设错误 |
| 不可逆的破坏性动作 | 删已发布的 tag、`--force` push、丢弃未提交的工作 |

### 一条容易被违反的

**「编译过了」「测试全绿」都不等于做完。** 六步里的第 ⑤ 步（操作测试）
要求你把应用真的跑起来点一遍。窗口装饰、拖拽、托盘图标这类问题
**没有一个是编译或单元测试能发现的**——只能靠真的去点。
详见 `shell/src-tauri/src/CLAUDE.md`。

## 5. 接手上一轮没做完的活

```bash
git log --oneline -5          # 上一轮做到哪
git status                    # 有没有未提交的改动
make check                    # 现在是绿的吗
make dev-status               # 有没有留下的服务进程
gh pr list                    # 有没有开着的 PR
```

然后读 **最近一次提交的 message** —— 本仓库要求提交信息写明
「先红的测试」与「验证命令」，那就是上一轮的交接单。

**如果 `make check` 是红的**：先修绿再干新活。带着红继续做，
下一轮 AI 分不清哪些红是你造成的。

## 6. 交给另一个 AI

**传契约，不传聊天记录**（格式见 `ai-workflow.md` §2）：

```yaml
goal: 一句话
allowed_changes: [具体路径]
forbidden_changes: [具体禁止项]
acceptance_criteria: [每条能变成一句断言]
stop_conditions: [什么情况必须停]
context: [该读哪份文档的哪一节 ← 不要说「读 docs/」]
```

`context` 那行是**上下文预算的关键**：指到章节，不指到文件。

## 7. 文档体量的硬规矩

| 层 | 上限 | 超了怎么办 |
|---|---|---|
| L0（根 `AGENTS.md` + `CLAUDE.md`） | **6k tok** | 把细节下沉到专题文档，只留路由 |
| 目录 `AGENTS.md` | **1.5k tok** | 拆子目录，或把详细规格挪进 `docs/` |
| skill | **2k tok** | 同上 |
| L2 专题文档 | 无上限，但 **>8k 必须有「读法」块** | 加章节索引 |

```bash
make check-doc-budget    # CI 会跑
```

**写文档时问一句：这份会在什么时候被读？** 答不上来就说明它放错层了。
