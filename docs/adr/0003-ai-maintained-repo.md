# ADR 0003 · 把「无人类逐行审阅」当作一等约束

- **日期**：2026-08-07
- **状态**：已接受

## 背景

本仓库由 Claude 与 Codex 共同维护。项目所有者的原话：

> 「之前 AI 写的代码很乱，特别是后端。」

这不是个别失误，是**结构性问题**。AI 写代码有几个稳定的失控倾向：

| 倾向 | 原因 |
|---|---|
| 平铺 —— 一个包几十个文件 | 看不到全局，每次都往最近的文件里加 |
| 复制粘贴复用 | 复制比抽象省事，且不会破坏现有测试 |
| 重复造轮子 / 重复写测试 | 不知道上一轮写过什么 |
| 写假测试 | 断言真实行为难，让覆盖率好看容易 |
| 文档漂移 | 改代码不改文档，没有惩罚 |

普通团队靠 code review 兜住这些。**这里没有 code review。**

## 决策

### 1. 规则必须可被命令验证

> **写在文档里却没有检查手段的规则 = 无效规则。**

每加一条规范，同时问：这条怎么被 CI 拦？拦不了就改成能拦的形式，或明确标注「靠自觉，可能失效」。

已落地的强制手段：

| 规则 | 强制手段 |
|---|---|
| 关键目录必须有填实的 `AGENTS.md` + `CLAUDE.md` | `scripts/check/check-agent-docs.sh` |
| 工具库不许重复造轮子 | `scripts/check/check-util-index.sh` |
| 测试不许重复写 | `scripts/check/check-test-index.sh` |
| 垃圾桶文件名、文件超长、Get 前缀、TS enum、越层 import | `scripts/check/check-naming.sh` |
| 测试先行（提交必须写「先红的测试」） | `scripts/check/check-commit-msg.sh` |
| 分包覆盖率门槛 | `scripts/check/check-coverage.sh` |
| 中英词条一致、无硬编码文案 | `scripts/check/check-i18n.sh` + ESLint |
| 契约先行 | `make check-gen` |
| 分层依赖方向 | `golangci-lint` depguard |

### 2. 索引化：对抗「不知道已有什么」

AI 重复造轮子和重复写测试是**同一个根因**：它看不到已有的东西。

| 索引 | 挡什么 |
|---|---|
| `util/INDEX.md` | 重复实现工具函数 |
| `tests/INDEX.md` | 重复写功能相同的测试 |
| `.skills/README.md` | 重复定义流程 |

**索引不是文档，是被 CI 校验的清单。** 写新东西前先查索引是强制流程。

### 3. 文档自生长

目录会越来越多。**每个关键目录必须自带 `AGENTS.md` + `CLAUDE.md`，
谁在这个目录里干活谁补上**，和业务改动同一个提交。

关键在于每份文档必须写清「**不负责什么**」—— 边界比职责更能防止代码放错地方。

### 4. 双入口，单一真源

Codex 读 `AGENTS.md`，Claude Code 读 `CLAUDE.md`。
**`AGENTS.md` 是真源，`CLAUDE.md` 是三行薄壳**，只放 Claude 独有的东西。

`.skills/` 是 skill 真源，`.claude/skills` 与 `.agents/skills` 软链过去 —— 两端用同一套。

**任何内容都只在一处写，交叉引用用链接。** 重复的内容必然漂移。

### 5. 角色隔离：实现方不得审查自己的改动

Claude 实现 → Codex 审查；Codex 实现 → Claude 审查。

这直接对应产品自身的「实现审查员独立会话」机制。
自我审查在人类团队里就不可靠，在 AI 上更不可靠。

## 后果

**得到**

- 违规在 CI 上被拦，而不是在几十轮之后被人发现
- 新一轮 AI 靠索引和分域文档快速定位，不必重新理解全局
- 流程本身就是产品的原型验证 —— 自己都跑不通的流程不该做成产品

**付出**

- 前期投入大：写代码之前先写了一整套规范与检查脚本
- 每个改动的仪式更重（补文档、登记索引、写提交格式）
- 检查脚本本身也要维护，且要保证它们**真的会红**（永远绿的检查比没有检查更糟）

**接受的取舍**

仪式感换确定性。这个项目的失败模式不是「做得慢」，是「几十轮之后没人能看懂也不敢改」。
