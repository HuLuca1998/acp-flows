# ADR 0002 · 发布链路与客户端自动更新

- **日期**：2026-08-07
- **状态**：已接受
- **相关**：[`../release-and-update.md`](../release-and-update.md)

## 背景

设计稿里已经画完了应用更新（设置 → 应用更新），且用户指定这块**优先做**。
关键是设计稿里的一句话：

> 「更新前会暂停所有工作并保存检查点，重启后从检查点恢复。」

这意味着更新不是"下载装包重启"，而是一次**跨前后端的领域操作**。

## 决策

### 1. 版本号由提交信息推导，用 release-please

| 方案 | 否决理由 |
|---|---|
| **release-please** ✅ | 语言无关（本仓库是 Go + Rust + TS 混合），读 conventional commits，自动开 Release PR |
| changesets | 偏 JS 生态，混合仓库不顺手 |
| 手动打 tag | 无人类逐行审阅的仓库里，手动步骤 = 迟早出错 |

`tauri.conf.json` 的 `version` 是唯一版本号真源。**任何人不得手改。**

### 2. 发版由人点，其余全自动

```
PR 合入 main → release-please 开 Release PR → 【人合并】→ tag → 构建签名发布
```

**唯一需要人拍板的地方是合并 Release PR。**
理由：发版对外可见且不可撤回，对应产品自身的 D3 等级。

### 3. 两种签名，现在只做一种

| 签名 | 作用 | 决定 |
|---|---|---|
| **minisign**（Tauri updater） | 保证更新包未被篡改，客户端强制校验 | **立刻做** |
| Apple 代码签名 + 公证 | 让 Gatekeeper 放行 | **暂不做**（ad-hoc），首次安装需手动放行 |

CI 里预留公证步骤开关（`APPLE_*` secrets 存在时才执行），将来买了开发者账号
只需填 secrets，不改流水线。

> ⚠️ **minisign 私钥丢失 = 所有已安装客户端再也收不到更新**（公钥硬编码在旧版本里）。
> 生成后必须离线备份，不能只存在 GitHub Secrets 里。

### 4. `prepare` 是后端的领域操作，不是前端的形式步骤

用户点「一键更新并重启」后，**先调后端，不是先下载**：

```
POST /v1/system/update/prepare
```

后端逐个处理非终态的 Work：取消（两段式）→ 采集证据与事件游标 → 落检查点 → `paused`。

**返回 `blocked` 时前端不得继续安装**，要把卡住的工作显示给用户，
由用户选择「强制更新（丢弃 N 分钟工作）」还是「稍后」。

这条依赖 M0 的 `Work` 状态机与两段式取消。**实现顺序**：先做「无进行中工作时直接放行」，
状态机到位后补全。

### 5. 自动检查，绝不自动安装

设计稿写死了「自动检查更新（**不自动安装**）」。

- 后台每 6 小时 + 启动时检查
- 发现新版本 → 设置页角标 + 一条 `app` 事件
- **绝不自动下载、绝不自动安装、绝不自动重启**

理由：这个 App 在跑长任务写用户的代码。任何未经确认的重启都可能丢掉几十分钟的工作。

### 6. Runtime 更新是独立的第二条线

`claude-agent-acp` / `codex-acp` 从 npm 更新，装到多版本目录并存，
探针 12 项全过才允许切换默认版本。**不需要重启 App**，但有活跃会话时要等会话结束。

多版本并存让「切换版本」可用，也让升级出问题时能一键退回。

## 后果

**得到**

- 合一个 PR 就能发一个用户装得上、且能自动更新的版本
- 更新不会丢工作 —— 这是这个产品能被信任的前提
- Runtime 升级出问题可一键退回

**付出**

- `prepare` 的完整语义依赖 M0，M1 前期只能实现简化版
- ad-hoc 签名导致首次安装体验差（需用户手动放行）
- 需要维护 minisign 私钥，且丢了无解

**不做**

- 增量更新（Tauri 暂不支持）
- beta 通道（等有外部测试者）
- 回滚靠删 tag（**禁止**——已更新的客户端无法回退，只会制造版本混乱；
  出问题就发一个版本号更高的修复版）
