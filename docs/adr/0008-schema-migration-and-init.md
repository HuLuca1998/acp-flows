# ADR 0008 · 数据库迁移、版本更新与一键初始化

- **状态**：已接受
- **日期**：2026-08-07
- **相关**：[`0002`](0002-release-and-auto-update.md)（自动更新）· [`0005`](0005-persistence.md)（只用 SQLite）
- **落地**：[`../rules/database.md`](../rules/database.md) §5 · [`../spec/architecture.md`](../spec/architecture.md) §6 ·
  [`../plan/milestones/M1-release-and-update.md`](../plan/milestones/M1-release-and-update.md)

## 背景

Duet 会自动更新。**自动更新 + 本地数据库 = 一类特有的风险**，桌面应用尤其严重：

- 用户不是 DBA，没有备份习惯，出问题没有恢复手段
- 更新是自动的，用户不知道 schema 变了
- **用户可能装回旧版**（更新回滚、多机同步、手动降级）
- 迁移失败时数据库可能停在半途

原有设计只写了迁移文件怎么写（`database.md` §5），没有回答：
更新时迁移在什么时刻跑、失败了怎么办、装回旧版会怎样、全新安装怎么初始化。

---

## 决策

### D1 · schema 版本与 App 版本**解耦**

schema 版本是单调递增整数（迁移文件号），App 版本是 semver。**二者不做映射。**

一次发版可能带 0 个迁移，也可能带 3 个。强行映射会造出一个假约束，
以后每次发版都要维护它。

但每个二进制**内嵌它认识的最高 schema 版本**（= 嵌入的迁移文件里最大的号），
这是 D3 的判据。

### D2 · 迁移在 `duetd` 启动时跑，且在 `listen` 之前

```
duetd 启动 → 打开 DB → 检查降级(D3) → 备份(D4) → 迁移 → seed(D6) → listen HTTP
```

**不在请求路径上跑迁移。** Tauri 壳拉起 sidecar 后前端立刻发请求，
若迁移还在跑，第一个请求会超时或读到半个 schema。
迁移完成前不 listen —— 前端得到的是干净的「连不上」，不是脏数据。

### D3 ★ · 旧版程序遇到更高的 schema 版本必须**拒绝启动**

```
MAX(schema_migrations.version) > 本二进制内嵌的最高版本  →  退出，非零码
```

错误信息要能自解释：

```
数据库由更高版本的 Duet 建立（schema v7，本版本最高支持 v5）。
请升级 Duet，或从备份恢复：~/.acpflows/backup/
```

**这是本 ADR 最重要的一条。** 自动更新意味着降级是真实会发生的：
用户回滚版本、在两台机器上跑不同版本、从时间机器恢复了旧 App。

旧代码读新 schema **不会崩溃**——它会读到少了列的表、多了行的枚举，
然后**静默产生错误结果**。那比崩溃危险得多，因为没有任何人会发现。

### D4 ★ · 迁移前自动备份，且**必须用 `VACUUM INTO`**

```sql
VACUUM INTO '~/.acpflows/backup/duet-v<fromVersion>-<ts>.db';
```

**不能用文件拷贝。** 实测（本仓库探针）：

| 做法 | WAL 未 checkpoint 时的结果 |
|---|---|
| `cp duet.db backup.db` | ✗ **`no such table`** —— 数据还在 `-wal` 里，主库文件是空壳 |
| `VACUUM INTO` | ✓ 数据完整，且是一致性快照，不需要停写 |

> 原 `database.md` §5 写的是「备份 `duet.db` 到 `duet.db.bak-<version>`」，
> 那个措辞暗示文件拷贝，**是错的**。本 ADR 推翻它。

补充约束：

- **只在「确实有待应用迁移」时备份**。每次启动都拷一份，用户磁盘会被吃光
- `VACUUM INTO` **要求目标文件不存在**（实测报 `output file already exists`），
  所以文件名带时间戳，且写之前不要预创建
- 备份**失败即中止迁移**。没有退路的迁移不许开始

### D5 · 迁移失败：整体回滚，退出，**不自动恢复**

迁移已经在单个事务里（现有实现），失败会整体回滚。之后：

1. `duetd` 以非零码退出，stderr 与日志里写明**备份路径**
2. 壳显示可读的失败页，给出备份路径与「联系支持」
3. **不自动从备份恢复**

第 3 条是刻意的：那是用户的数据，恢复是破坏性操作，要用户点头。
自动恢复会掩盖问题，且可能覆盖掉用户在失败后又产生的数据。

### D6 · 种子数据与迁移**分开**

迁移只管 schema。种子数据（推荐角色集、默认设置）走独立的幂等 seed 步骤：

```sql
INSERT INTO roles (id, ...) VALUES ('role.reviewer', ...) ON CONFLICT(id) DO NOTHING;
```

**为什么不塞进迁移**：迁移的 checksum 被锁死，改了就报错。
但种子内容**会随产品演进**——推荐角色集一定会调整。塞进迁移就永远改不了了。

seed 用稳定 ID + `ON CONFLICT DO NOTHING`，每次启动都跑，幂等。
**不覆盖用户已改过的记录**。

### D7 · 一键初始化 = 首次自动 + 手动重置

| 场景 | 行为 |
|---|---|
| **首次启动**（数据目录不存在） | 自动建目录 → 从 0 跑全部迁移 → seed。无需用户操作 |
| **手动重置**（设置页 / `duetd --reset`） | 先 `VACUUM INTO` 备份 → 删库 → 重新初始化。**二次确认** |
| **开发态** | `make db-reset`（直接删 `~/.duet-dev`，不备份——它就是用来糟蹋的） |

「一键初始化」在正常路径上应该是**不可见**的：用户第一次打开就能用，
不该看到任何「正在初始化数据库」的界面。

### D8 · 与更新流程的咬合

```
① prepare      暂停所有工作、落检查点        （M1 S1.7，已有设计）
② 装新版本
③ 新 duetd 启动 → D3 降级检查 → D4 备份 → 迁移 → D6 seed → listen
④ 壳恢复被暂停的工作
```

**③ 失败时 ④ 不执行**，工作停在检查点上——这正是 ① 存在的意义。

---

## 取舍

**没有 down 迁移。** 回退靠备份，不靠反向 SQL。
理由：down 迁移在桌面应用上几乎从不被执行，写了也没测过，
真出事时它本身就是新的风险源。备份是确定性的。

**没有「迁移进度界面」。** 本地 SQLite 的迁移是毫秒级的。
真到了需要进度条的数据量，说明该重新考虑存储方案了。

**D3 的代价**：用户降级后 App 起不来，体验上是"坏了"。
接受这个代价——静默的数据损坏是不可接受的，而这个失败态是可解释、可恢复的。

## 后果

需要新增的能力（落进 M1）：

| 能力 | 位置 |
|---|---|
| 内嵌最高 schema 版本 + 降级检查 | `store/migration` |
| `VACUUM INTO` 备份 + 保留策略 | `store/backup.go`（新） |
| seed 步骤 | `store/seed/`（新） |
| `--reset` 与设置页入口 | `cmd/duetd` + 前端设置页 |
| 启动顺序：迁移完成才 listen | `cmd/duetd` |

必须有的测试：

- 降级检查：schema 版本高于内嵌版本时**拒绝启动**（不是警告）
- 备份：WAL 有未 checkpoint 数据时，备份里的数据**完整**
- 备份失败 → 迁移不开始
- 迁移失败 → 整体回滚，库仍停在旧版本可用状态
- seed 幂等：跑两次结果一样；**用户改过的记录不被覆盖**
- 首次启动：空目录 → 可用状态，零用户操作
