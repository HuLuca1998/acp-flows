# 里程碑体系

> [`../roadmap.md`](../roadmap.md) 是**总览**（有哪些里程碑、为什么这个顺序）。
> 本目录是**分章**：每个里程碑一份，拆到可执行的单元与可断言的验收标准。

## 结构与产品同构 —— 这是刻意的

```
里程碑 Milestone   ≈  PlanVersion
  └ 子计划 Subplan  ≈  Subplan（构成 DAG，有依赖）
      └ 单元 Unit    ≈  Unit + UnitContract（冻结的写入边界与验收标准）
          └ 验收标准 ≈  acceptance_criteria（每条对应一个测试断言）
```

**我们自己先跑一遍 Duet 要产品化的流程。** 自己都跑不通的流程，不该做成产品卖给别人。

副作用是一个免费的真实数据集：M0 结束时，这些文档本身就是 Duet 第一批
`PlanVersion` / `UnitContract` 的样本，可以直接喂给 Fake Runtime 做夹具。

## 编号规则

```
M<里程碑>            M0
S<里程碑>.<子计划>    S0.1
U<里程碑>.<子计划>.<单元>   U0.1.2
```

编号**只增不复用**。单元合并或废弃时保留编号并标注，不要让后面的号往前挪——
分支名、issue、提交信息里都引用了它。

分支名直接用编号：`feat/acp-u0-1-2-fake-runtime`。

## 每个单元必须写全五段

照抄产品的 `UnitContract` 字段，**一段都不能省**：

| 段 | 内容 | 省了会怎样 |
|---|---|---|
| `goal` | 一句话，说清做完之后什么变得可能了 | 做着做着跑偏 |
| `allowed_changes` | 允许改的文件/目录，**具体到路径** | 边界形同虚设 |
| `forbidden_changes` | 明确禁止碰的东西 | 「顺手改一下」 |
| `acceptance_criteria` | 逐条，**每条必须能变成一句可执行断言** | 无法测试先行 |
| `stop_conditions` | 什么情况必须停下来上报 | AI 自行扩大范围 |

**写不出可断言的验收标准 = 这个单元还没想清楚。** 回去拆，不要开工。

## 状态标记

每个单元行首用一个标记，**完成时就地改**，不要另开进度表：

| 标记 | 含义 |
|---|---|
| `○` | 未开始 |
| `◐` | 进行中（标注分支名） |
| `✓` | 已验收（**标注 PR 号**） |
| `⊘` | 已废弃（**必须写原因**） |

## 依赖与并行

每章开头画子计划 DAG。**无依赖关系的子计划可以并行**，用 worktree 隔离
（见 [`../git-workflow.md`](../git-workflow.md) §4）。

并行的前提是**文件不重叠**。切不开就别并行——串行比合并冲突便宜。

## 什么时候改这些文档

| 情况 | 动作 |
|---|---|
| 单元做完 | 就地改标记为 `✓` + PR 号 |
| 发现单元拆错了 | **加新单元，不改已验收的**（对应 PlanVersion 的 append-only） |
| 发现整个子计划的假设错了 | 停下来，判定 `global_replan`，找人 |
| 验收标准写不出断言 | 说明没想清楚，回去拆细 |

**不要在这里写实现细节。** 单元只说「做什么、边界在哪、怎么算完」，
「怎么做」在对应的专题文档里（`acp-integration.md` / `frontend-guide.md` / …）。
