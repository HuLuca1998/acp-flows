## 这个包干什么

**一条 ACP 会话**：建会话、发需求、把 Agent 说的话流式交出去、裁决它要的权限。

它只管「一轮对话怎么跑通」。谁在什么时候拉起它、事件怎么落库，都不在这里
（那是 `acp/agent` 与 `app/work` 的事）。

---

## 本目录的铁律

### 1. 事件同步投递，不过 channel

`Prompt` 的 `onEvent` 在事件到达时**立即同步调用**。

第一版用带缓冲的 channel + goroutine 转发，结果丢事件：`session/prompt` 的
响应回来后 `Prompt` 就关掉 channel，而最后几条通知可能还在 jsonrpc 的读循环里
没处理完。同步投递让顺序天然正确。

代价是 `onEvent` 跑在 jsonrpc 的读 goroutine 上——**里面不要做慢操作**。

### 2. 权限裁决：绝不猜 optionId ★

`optionId` 是 Agent 自己定义的**不透明字符串**。三条不能破：

| 场景 | 必须怎么做 | 破了会怎样 |
|---|---|---|
| 策略想允许，但没有 allow 类选项 | 交给用户 | 猜一个 = 可能替他点了「永久允许」 |
| 用户选了某个 id | **原样回传** | 按类别重新匹配 = 用户点「拒绝」而 Agent 收到「允许」 |
| 没配 `AskUser` / 用户没选 | 回 `cancelled` | 随便挑一个 = 关掉窗口等于默认同意 |

`allow_once` 与 `allow_always` 都在时**选 once**：替用户做的决定要尽量小。

### 3. 只读是白名单，不是黑名单

`readonlyKinds` 列的是「只看不动」的类别。反过来列危险的话，Agent 新增一类
工具时会默认落进「自动允许」——用户以为自己开的是「让它随便看」，
实际开的是「让它随便改」，而他不会发现，直到文件被改了。

### 4. 阻塞只阻塞这一轮

等用户裁决时**不许拿全局锁**。用户开着两个工作、去泡杯咖啡回来，
不该发现两个都停在那儿——他只被问了一件事。

### 5. Close 有界等待

Agent 一轮结束后**并不退出**（它等着下一条需求），而读循环要等对方关掉 stdout。
死等的话两边互相等，表现是应用退不出去、Agent 进程越攒越多。
超时不算错误——真正的收尾（杀进程组）归调用方的 `runtime.Process.Stop` 管。

## 测试怎么写

对手方是 `acp/fake` 的 Fake Runtime：它按官方规范独立说话（只许 import
`protocol`），所以「我们理解错了协议」这件事测得出来。换成 mock 的话，
mock 和被测代码会一起错、测试照样绿。

写 `*_test.go` 前先调 `go-unit-testing` skill。
每加一条断言，问一遍「把实现改坏，它会不会红」——**造负例，别猜**。

> R3 那条测试的教训：第一版让 B 会话跑一个**没有权限请求**的脚本，
> 于是给裁决加一把全局锁它照样绿。B 必须真的走到被测那段代码。
